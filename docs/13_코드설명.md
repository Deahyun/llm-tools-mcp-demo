## 0장. 실행해 보기

11/12번과 달리 **터미널이 두 개** 필요합니다. 그것이 이 예제의 요점입니다.

```powershell
# 터미널 A — 서버 (계속 떠 있음)
python demo\13_mcp_http_server.py

# 터미널 B — 클라이언트 (몇 번이든 반복 실행 가능)
python demo\13_mcp_http_client.py
python demo\13_mcp_http_client.py "hello 로 test 해줘"
```

**터미널 B (클라이언트):**

```
======================================================================
[13] MCP (streamable http)   model=qwen3.8-local:27b   host=http://127.0.0.1:11434
[13] MCP 서버: http://127.0.0.1:8932/mcp
질의: hello 로 test 해줘
======================================================================
[mcp] list_tools -> ['test']
[1] 도구 호출: test({'a': 'hello'})  <- MCP over HTTP
[1] 도구 결과: {'ok': True, 'result': '123---hello---456'}
[2] 도구 호출 없음 -> 종료
----------------------------------------------------------------------
`123---hello---456`
```

**터미널 A (서버):**

```
[server] demo-test-tool-http
[server] http://127.0.0.1:8932/mcp 에서 대기 중 (Ctrl+C 로 종료)
StreamableHTTP session manager started
[mcp] list_tools -> test
[mcp] call_tool test({'a': 'hello'})
123---hello---456                        ← test() 의 print 는 여기에만 찍힌다
```

여기서 가장 중요한 것을 먼저 보세요. **`123---hello---456` 이라는 print는 서버 콘솔에만
있습니다.** 클라이언트가 받은 것은 `{'ok': True, 'result': ...}` 라는 JSON 응답뿐입니다.
함수가 클라이언트 쪽에서 돌지 않았다는 증거입니다.

포트를 바꾸려면 양쪽에 알려 줍니다.

```powershell
python demo\13_mcp_http_server.py --port 9000
python demo\13_mcp_http_client.py --url http://127.0.0.1:9000/mcp
```

## 1장. 왜 파일을 둘로 나눴나

12번(stdio)은 한 파일이 서버와 클라이언트를 겸했습니다. 실행이 편하다는 장점이 있지만
대신 헷갈리는 지점이 생깁니다.

> "이 파일에 `test()` 가 있는데, 클라이언트도 이 함수를 쓰는 건가?"

답은 "아니오"입니다. 한 파일이 두 프로세스로 각각 로딩되고, 프로세스마다 실행되는 부분이
다를 뿐입니다. 하지만 **코드만 봐서는 그 경계가 보이지 않습니다.**

13번은 그 경계를 파일로 그었습니다.

```
13_mcp_http_server.py            13_mcp_http_client.py
  ├ test()          ← 도구         ├ (도구 없음)
  ├ TOOL_* 명세                    ├ to_ollama_schemas()  ← 받아온 명세를 번역만
  ├ on_list_tools()                ├ run_agent()          ← 에이전트 루프
  ├ on_call_tool()                 └ Client(url) ──────┐
  └ uvicorn ◀──────────────── HTTP ────────────────────┘
```

클라이언트 파일을 아무리 뒤져도 `def test` 는 나오지 않습니다. 그래서 이 파일만 읽는
사람은 **어떤 도구가 있는지 알 수 없습니다.** 알아내는 방법은 하나뿐입니다.

```python
listed = await mcp.list_tools()  # 서버에게 물어본다
```

이것이 MCP의 본질입니다. 도구를 프로세스 밖으로 밀어내면, 도구를 쓰는 쪽은 도구를
몰라도 됩니다. 실제 배포에서 서버와 클라이언트가 다른 저장소, 다른 언어, 다른 머신일 수
있는 이유입니다.

## 2장. stdio와 HTTP는 무엇이 다른가

12번(stdio):

```
클라이언트 ── spawn ──▶ 서버 (자식 프로세스)
           파이프로 대화. 클라이언트가 끝나면 서버도 사라짐. 1:1 전용.
```

13번(Streamable HTTP):

```
서버 (독립 프로세스, 포트를 열고 대기)
   ▲        ▲        ▲
클라이언트  클라이언트  다른 언어/다른 머신의 클라이언트
   URL 로 접속. 서버는 계속 살아 있음. 1:N.
```

| | stdio (12) | HTTP (13) |
|---|---|---|
| 연결 | 파이프(stdin/stdout) | 소켓(TCP) |
| 서버 수명 | 클라이언트에 종속 | 독립 |
| 동시 접속 | 1:1 | 1:N |
| 원격 | 불가 (같은 머신) | 가능 |
| 준비 | 없음 (자동 기동) | **서버를 먼저 띄워야 함** |
| 서버의 `print()` | **금지** | 자유 |
| 인증 | 프로세스 경계가 곧 경계 | **직접 챙겨야 함** |

아래 세 줄이 실무에서 크게 갈립니다. 편의를 잃는 대신(서버를 챙겨야 함) stdout 제약이
사라지고 확장성을 얻습니다. 그리고 네트워크에 열리므로 누가 접속할 수 있는지를 우리가
책임져야 합니다(11장).

## 4장. 서버 — 도구는 여기에만 있다

```python
def test(a: str) -> str:
    res = "123---" + a + "---456"
    print(f"{res}")
    return res


TOOL_NAME = "test"
TOOL_DESCRIPTION = (
    "문자열 하나를 받아 앞에 '123---', 뒤에 '---456' 을 붙여 돌려준다. "
    "사용자가 어떤 값을 test 해 달라고 하면 반드시 이 도구를 호출한다. "
    "직접 문자열을 만들어 답하지 말고 도구의 반환값을 그대로 사용한다."
)
TOOL_INPUT_SCHEMA: dict[str, Any] = {
    "type": "object",
    "properties": {
        "a": {"type": "string", "description": "가공할 문자열. 예: 안녕하세요"},
    },
    "required": ["a"],
}
```

11번의 `TOOL_SCHEMA` 한 덩어리가 세 조각으로 나뉘어 있을 뿐, 내용은 같습니다.
MCP의 `Tool` 객체가 이 셋을 따로 받기 때문입니다.

`description` 이 왜 이렇게 쓰여 있는지는
[11_코드설명.md 5장](11_코드설명.md#5장-tool_schema--모델이-실제로-보는-것) 을 보세요.
**여기 적은 설명이 그대로 모델에게 갑니다** — 도구가 서버에 있든 클라이언트에 있든,
모델이 도구를 고르는 근거는 이 문장입니다. 도구를 서버로 옮겨도 이 원칙은 변하지 않습니다.

주목할 점: 이 파일에는 `ollama` import가 없습니다. **서버는 LLM을 모릅니다.**
누가 자기를 부르는지 신경 쓰지 않고 도구만 제공합니다. 그래서 같은 서버에 Claude Desktop이
붙어도, 다른 에이전트가 붙어도 동작합니다.

## 5장. 서버 — 핸들러는 12번 그대로, `print()`는 자유

```python
async def on_list_tools(ctx, params) -> types.ListToolsResult:
    logger.info("[mcp] list_tools -> %s", TOOL_NAME)
    return types.ListToolsResult(
        tools=[
            types.Tool(name=TOOL_NAME, description=TOOL_DESCRIPTION, input_schema=TOOL_INPUT_SCHEMA)
        ]
    )
```

12번과 글자 하나 다르지 않습니다(로그 한 줄 제외). **핸들러는 자기가 어떤 트랜스포트 위에서
도는지 모릅니다.** 이것이 MCP 계층 분리의 이득입니다.

`input_schema` 는 SDK 2.x 필드명입니다. 1.x의 `inputSchema` 를 쓰면 에러가 납니다
([12_코드설명.md 4장](12_코드설명.md#4장-서버-1--on_list_tools) 의 버전 대조표 참고).

```python
async def on_call_tool(ctx, params) -> types.CallToolResult:
    ...
        else:
            payload = {"ok": True, "result": test(a)}      # 12번에는 여기에 redirect 가 있었다
```

12번에서 꼭 필요했던 두 줄이 사라졌습니다.

```python
# 12번 (stdio)
with contextlib.redirect_stdout(sys.stderr):
    payload = {"ok": True, "result": test(a)}
```

HTTP에서는 프로토콜이 **소켓**으로 흐르므로 `print()` 가 stdout으로 나가도 아무것도
깨지지 않습니다. 그냥 서버 콘솔에 찍힐 뿐입니다(0장 터미널 A 출력).

> 이 대비를 기억해 두면 실무에서 유용합니다. **"MCP 서버에서 print 금지"는 MCP의 규칙이
> 아니라 stdio 트랜스포트의 규칙입니다.** 트랜스포트가 무엇인지 모르면 제약의 범위를
> 잘못 외우게 됩니다.

실패를 `is_error` 가 아니라 `{"ok": false, "error": ...}` 페이로드로 보내는 것도
12번과 같습니다. 이유는
[12_코드설명.md 5장](12_코드설명.md#5장-서버-2--on_call_tool-과-stdout-금지-규칙) 참고.

## 6장. 서버 — ASGI 앱과 uvicorn

```python
def main() -> None:
    ...
    app = server.streamable_http_app(streamable_http_path=HTTP_PATH, host=args.host)
    ...
    uvicorn.run(app, host=args.host, port=args.port, log_level="warning")
```

**(1) `streamable_http_app()`** — MCP SDK가 우리 `server` 객체를 감싸 **ASGI 앱**을
만들어 줍니다. ASGI는 파이썬 비동기 웹 애플리케이션의 표준 인터페이스입니다. 즉 우리
MCP 서버가 웹 앱 한 개가 됩니다. `streamable_http_path="/mcp"` 는 그 앱 안에서 MCP가
응답할 경로이고, 그래서 접속 URL이 `http://127.0.0.1:8932/mcp` 입니다.

**(2) uvicorn** — ASGI 앱을 실제로 포트에 물려 돌려 주는 서버입니다. 앱은 "요청이 오면 뭘
할지"만 알고, 소켓을 열고 듣는 일은 uvicorn이 합니다.

**(3) `def` 이지 `async def` 가 아니다** — 이 예제 전체에서 유일한 예외입니다.

```python
def main() -> None:  # async def 가 아니다
    ...
    uvicorn.run(app, ...)  # asyncio.run() 으로 감싸지 않는다
```

`uvicorn.run()` 은 **자기가 직접 이벤트 루프를 만들어 돌립니다.** 이것을 `asyncio.run()`
안에서 부르면 "이미 루프가 돌고 있다"는 에러가 납니다. `asyncio.run()` 은 한 프로세스에서
중첩해 부를 수 없습니다.

정리하면 이렇습니다.

| 파일 | 이벤트 루프 주인 | 진입 방식 |
|---|---|---|
| 서버 | uvicorn | `main()` 을 그냥 호출 |
| 클라이언트 | 우리 | `asyncio.run(main())` |

## 7장. 클라이언트 — 도구 코드가 한 줄도 없다

클라이언트 파일의 import를 보세요.

```python
from mcp import Client
from ollama import AsyncClient
```

`test` 도, `TOOL_*` 도, `mcp.server` 도 없습니다. 이 프로세스는 **도구를 제공하지 않고
소비만 합니다.** 대신 두 가지를 서버에 물어보고 맡깁니다.

```python
listed = await mcp.list_tools()  # 어떤 도구가 있나?
response = await mcp.call_tool(name, arguments)  # 이걸 실행해 줘
```

11번(native)에서는 이 두 가지가 코드 안에 있었습니다.

| | 11번 native | 13번 client |
|---|---|---|
| 어떤 도구가 있나 | `TOOL_SCHEMA` 를 읽는다 | `list_tools()` 로 **물어본다** |
| 어떻게 실행하나 | `test(a)` 를 부른다 | `call_tool()` 로 **맡긴다** |
| 도구가 바뀌면 | 이 파일을 고친다 | **고칠 것이 없다** |

세 번째 줄이 실익입니다. 서버가 도구를 추가하면 클라이언트는 아무것도 안 해도 새 도구가
모델에게 노출됩니다(10장 실험 2).

### 받아온 명세를 모델 형식으로 번역

MCP의 도구 형식과 Ollama가 요구하는 형식은 모양이 다릅니다.

```python
def to_ollama_schemas(mcp_tools) -> list[dict[str, Any]]:
    return [
        {
            "type": "function",
            "function": {
                "name": t.name,
                "description": t.description or "",
                "parameters": t.input_schema or {"type": "object", "properties": {}},
            },
        }
        for t in mcp_tools
    ]
```

이 번역을 거치고 나면 **모델에게 보내는 `tools` 배열은 11번의 `TOOL_SCHEMA` 와 사실상
같아집니다.** 서버에서 세 조각으로 흩어져 있던 이름/설명/스키마가 여기서 다시 하나로
합쳐집니다.

> **모델은 MCP를 쓰는지 모릅니다.** 모델이 보는 것은 어느 쪽이든 같은 tools 배열입니다.
> MCP는 모델 바깥, 우리 코드와 도구 사이의 문제입니다.

## 8장. 클라이언트 — `Client(url)` 한 줄만 바뀐다

```python
async def run_agent(url: str, query: str) -> str:
    ollama = AsyncClient(host=OLLAMA_HOST)

    async with Client(url) as mcp:  # 12번: Client(server_params())
        listed = await mcp.list_tools()
        schemas = to_ollama_schemas(listed.tools)
```

12번과 **딱 한 곳** 다릅니다. `Client()` 에 `StdioServerParameters` 대신 URL 문자열을
넘깁니다. SDK가 인자 타입을 보고 트랜스포트를 고릅니다.

이 저장소 본체([`mcp_/client_agent.py`](../src/toolsdemo/mcp_/client_agent.py))도 같은 성질을
이용해 트랜스포트를 환경변수로 고릅니다.

```python
def client_target():
    if settings.mcp_transport == "http":
        return settings.mcp_http_endpoint  # 문자열이면 HTTP
    return server_params()  # 아니면 stdio
```

`run()` 은 한 줄도 달라지지 않습니다.

### 실행 위임

```python
async def call_tool(name: str, arguments: dict[str, Any]) -> dict[str, Any]:
    try:
        response = await mcp.call_tool(name, arguments)
    except Exception as exc:
        return {"ok": False, "error": f"MCP 호출 실패: {type(exc).__name__}: {exc}"}
    text = first_text(response)
    if text is None:
        return {"ok": False, "error": "MCP 응답에 텍스트 콘텐츠가 없습니다."}
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        return {"ok": True, "text": text}
```

방어가 세 겹인 이유는 12번과 같습니다 — 통신은 함수 호출보다 실패할 구석이 많고,
**어떤 실패든 예외로 죽지 않고 dict로 모델에게 전달되어야** 합니다.

### 그 아래 에이전트 루프

`run_agent()` 의 나머지(147줄 이후)는 11/12번과 **구조가 같습니다.**
messages를 만들고, `chat()` 하고, `tool_calls` 가 없으면 종료하고, 있으면 실행해서
`role: "tool"` 로 되돌립니다.
[11_코드설명.md 8장](11_코드설명.md#8장-run_agent--대화가-자라는-과정) 을 그대로 읽으면 됩니다.

**그 사실 자체가 이 예제의 결론입니다.** 트랜스포트를 바꿔도, 파일을 나눠도 에이전트 루프는
손대지 않습니다.

### `_root_cause()` — 가장 안쪽 원인 찾기

```python
def _root_cause(exc: BaseException) -> str:
    seen = exc
    for _ in range(10):  # 순환 참조 방어
        inner = getattr(seen, "exceptions", None)  # ExceptionGroup 이면 자식들이 들어 있다
        if inner:
            seen = inner[0]
            continue
        if seen.__cause__ is not None:  # raise ... from ... 으로 연결된 원인
            seen = seen.__cause__
            continue
        break
    return f"{type(seen).__name__}: {seen}"
```

MCP/anyio는 여러 태스크를 동시에 돌리므로 예외를 **ExceptionGroup** 으로 감싸 던집니다.
겉면만 보면 원인을 알 수 없어서, `exceptions` 와 `__cause__` 를 따라 가장 안쪽까지
내려갑니다.

파이썬 3.11+ 라면 `except*` 문법으로 더 깔끔하게 쓸 수 있지만, 이 저장소는
**Python 3.10 상한**을 지키므로 속성을 직접 따라갑니다. `range(10)` 은 예외 체인이
순환하는 병적인 경우에 무한 루프가 되지 않게 하는 안전장치입니다.

`raise` 로 다시 던지지 않고 `return 1` 로 끝내는 것도 의도입니다. 학습용 예제에서
traceback은 정보가 아니라 소음이고, 종료 코드 1이면 스크립트에서 실패를 감지하기에
충분합니다.

## 11장. 언제 HTTP를 쓰나 / 보안 주의

### stdio로 충분한 경우

- 도구를 나만 쓴다
- 서버와 클라이언트가 같은 머신, 같은 사람 소유
- 실행할 때만 잠깐 필요하다

이 경우 stdio(12번)가 낫습니다. 준비할 것이 없고, 클라이언트가 끝나면 서버도 사라져
관리가 없습니다.

### HTTP가 필요한 경우

- **여러 클라이언트**가 같은 도구를 쓴다
- 서버가 **상태를 유지**해야 한다 (예: 이 저장소 본체는 브라우저 세션을 여러 실행에 걸쳐 재사용)
- 서버가 **다른 머신**에 있거나 **다른 언어**로 짜였다
- 서버 기동 비용이 커서 매번 띄우기 아깝다

### 보안

이 예제 서버에는 **인증이 없습니다.** 그래서 기본 바인딩이 `127.0.0.1`(루프백)입니다 —
같은 PC에서만 접속됩니다.

`--host 0.0.0.0` 으로 열면 네트워크의 누구나 이 서버의 도구를 호출할 수 있게 됩니다.
지금은 문자열을 가공할 뿐이지만, 도구가 파일을 읽거나 브라우저를 조작한다면 그 권한을
통째로 여는 셈입니다. **학습용 코드를 그대로 외부에 열지 마세요.**

> 참고로 `0.0.0.0` 은 **바인딩 주소**이지 접속 주소가 아닙니다. 클라이언트가 가진
> `normalize_host()` 가 다루는 함정과 같은 개념입니다
> ([11_코드설명.md 3장](11_코드설명.md#3장-설정-블록과-ollama_host-함정)).

## 13장. 요즘은 이렇게 짧게 쓴다 — 고수준 API

지금까지 읽은 [`13_mcp_http_server.py`](../demo/13_mcp_http_server.py) 는 **저수준 API**로
짜였습니다. `on_list_tools` / `on_call_tool` 을 손으로 쓰고, `types.Tool` 과
`types.CallToolResult` 를 직접 조립하고, `uvicorn` 을 직접 부릅니다.

프로토콜이 무엇을 주고받는지 배우기에는 이 편이 좋습니다. 하지만 **오늘 실무에서 MCP 서버를
새로 만든다면 대개 고수준 API를 씁니다.** SDK 2.x의 `MCPServer` 가 그것이고,
[`demo/13_mcp_fastapi_style.py`](../demo/13_mcp_fastapi_style.py) 가 같은 서버를 그 방식으로
다시 쓴 것입니다.

```powershell
# 저수준 판 대신 이걸 띄운다. 포트도 경로도 같다.
python demo_mcp_fastapi_style.py

# 클라이언트는 그대로. 한 글자도 안 고친다.
python demo_mcp_http_client.py "hello 로 test 해줘"
```

### 무엇이 사라지는가

```python
from mcp.server import MCPServer

mcp = MCPServer("demo-test-tool-http", version="0.1.0")


@mcp.tool(name="test", description="문자열 하나를 받아 앞에 '123---' ...")
def test_tool(a: Annotated[str, Field(description="가공할 문자열. 예: 안녕하세요")]) -> dict:
    return {"ok": True, "result": test(a)}


mcp.run(transport="streamable-http", host=..., port=..., streamable_http_path="/mcp")
```

두 파일 다 주석과 docstring이 절반 이상이라 겉보기 줄 수 차이는 크지 않습니다.
설명을 걷어내고 **실제 코드만 세면 76줄 대 33줄**입니다.

데코레이터 한 덩어리가 저수준 판의 여섯 가지를 대신합니다.

1. 타입 힌트 `a: str` → JSON Schema `{"a": {"type": "string"}}` 생성
2. `Annotated[..., Field(description=...)]` → 그 인자의 `description` 채우기
3. `list_tools` 요청이 오면 이 도구를 목록에 담아 응답
4. `call_tool` 요청이 오면 인자를 검증해 함수 호출
5. 반환값을 `TextContent` 로 포장 (+ `structured_content` 도 함께)
6. 함수가 예외를 던지면 `is_error` 결과로 변환

그리고 `mcp.run()` 이 ASGI 앱 생성부터 서빙까지 처리하므로 `uvicorn` import 도 사라집니다.
`transport="stdio"` 로 바꾸면 같은 서버가 12번처럼 stdio 로 뜹니다 — 트랜스포트가 인자
하나가 됩니다.

| | 저수준 `Server` | 고수준 `MCPServer` |
|---|---|---|
| 도구 등록 | `on_list_tools` 에서 `types.Tool` 조립 | `@mcp.tool()` |
| 스키마 | 손으로 쓴 JSON Schema | 타입 힌트에서 **자동 생성** |
| 도구 실행 | `on_call_tool` 에서 분기 | 자동 디스패치 |
| 결과 포장 | `CallToolResult(content=[TextContent(...)])` | 반환값을 자동 포장 |
| 서빙 | `uvicorn.run(server.streamable_http_app(...))` | `mcp.run("streamable-http")` |
| 인증 | 직접 | `auth_server_provider` / `token_verifier` 인자 |
| 서버 파일 길이 | 155줄 (설명 제외 76줄) | 127줄 (**설명 제외 33줄**) |

### 클라이언트는 차이를 모른다

이것이 이 장의 요점입니다. 고수준 서버를 띄우고 **수정하지 않은** 클라이언트를 붙이면
이렇게 나옵니다.

```
[mcp] list_tools -> ['test']
[1] 도구 호출: test({'a': 'hello'})  <- MCP over HTTP
[1] 도구 결과: {'ok': True, 'result': '123---hello---456'}
`123---hello---456`
```

저수준 서버를 붙였을 때와 **글자 하나 다르지 않습니다.** 프로토콜로 나가는 것이 같기
때문입니다. 서버를 어떻게 짰는지는 서버의 사정이고, 클라이언트와 모델은 알 필요가 없습니다.

### 그런데 두 가지 함정이 있다

**함정 1 — 인자 설명은 자동으로 안 나옵니다.**

고수준 API는 타입 힌트에서 스키마를 만들지만 **docstring의 `Args:` 절은 파싱하지 않습니다.**
`Field(description=...)` 를 빼고 그냥 `def test_tool(a: str)` 로 두면 스키마가 이렇게 됩니다.

```json
{"a": {"title": "A", "type": "string"}}
```

`description` 이 없습니다. 모델은 `a` 가 무엇인지 알 방법이 사라집니다. "docstring이 곧
프롬프트"라는 원칙([11_코드설명.md 5장](11_코드설명.md#5장-tool_schema--모델이-실제로-보는-것))을
지키려면 `Annotated + Field` 한 줄이 필요합니다. 붙이고 나면 이렇게 나옵니다.

```json
{"a": {"description": "가공할 문자열. 예: 안녕하세요", "title": "A", "type": "string"}}
```

> 참고로 이 저장소 본체는 이 문제를 다르게 풉니다. [`tools/registry.py`](../src/toolsdemo/tools/registry.py)
> 의 `@tool` 데코레이터가 **docstring의 `Args:` 를 직접 파싱해** description을 채웁니다.
> 그래서 도구 작성자는 평범한 Google 스타일 docstring만 쓰면 됩니다.

**함정 2 — 실패 표현이 달라질 수 있습니다.**

위 6번(`예외 → is_error`)은 편해 보이지만, 이 예제들이 지켜 온 규약과 **다른 동작**입니다.
11/12/13 저수준 판은 실패를 `{"ok": false, "error": ...}` 라는 **데이터**로 돌려줘
LLM이 읽고 스스로 고쳐 재시도하게 했습니다. 예외를 던져 `is_error` 가 되면 그 복구 경로가
끊깁니다.

그래서 [`13_mcp_fastapi_style.py`](../demo/13_mcp_fastapi_style.py) 의 도구는 `str` 이 아니라
**`dict` 를 반환합니다.**

```python
def test_tool(a) -> dict:
    return {"ok": True, "result": test(a)}
```

`str` 을 그대로 반환하면 SDK가 평문 텍스트로 포장해 보내고, 클라이언트의 `json.loads` 가
실패해 폴백 경로로 갑니다. 실제로 처음 짰을 때 이렇게 갈렸습니다.

```
저수준 서버:  {'ok': True, 'result': '123---hello---456'}
고수준 서버:  {'ok': True, 'text':   '123---hello---456'}    ← 폴백
```

최종 답변은 같았지만 **페이로드 규약이 어긋난 것**입니다. dict를 반환하도록 바꾸니 둘이
일치했습니다. 고수준 API가 편의를 주는 대신 이런 세부는 눈에 덜 띄게 만든다는 예입니다.

### 그럼 저수준은 언제 쓰나

- 프로토콜을 세밀하게 제어해야 할 때 (진행 알림, 커스텀 콘텐츠 타입 등)
- **도구 정의를 다른 곳이 이미 갖고 있을 때** — 이 저장소 본체가 그렇습니다.
  도구는 `tools/registry.py` 가 소유하고 [`mcp_/server.py`](../src/toolsdemo/mcp_/server.py) 는
  그것을 프로토콜로 **번역만** 합니다. 고수준 API는 도구 정의를 자기가 소유하려 하므로
  Phase 1(native)과 정의를 공유하기가 껄끄러워집니다.
- 프로토콜이 실제로 무엇을 주고받는지 **배울 때** — 이 문서 5장이 그 목적입니다.

정리하면, **새 서버를 처음부터 만든다면 고수준이 기본값**이고, 저수준은 위 세 경우에
고르는 선택지입니다. 두 파일을 나란히 놓고 읽으면 고수준 API가 무엇을 대신해 주는지가
분명해집니다.

## 세 예제를 마치며

| | 11 native | 12 MCP stdio | 13 MCP http |

표의 아래 네 줄이 세 예제의 결론입니다. **도구를 어떻게 조달하든 모델이 보는 것과 결과는
같습니다.** 그래서 도구는 한 번만 잘 설계하면 되고, 조달 경로는 나중에 필요에 따라 바꿀 수
