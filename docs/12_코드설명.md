## 0장. 실행해 보기

**서버를 따로 띄울 필요가 없습니다.** 이 파일이 자기 자신을 서버로 기동합니다.

```powershell
python demo\12_mcp_local.py
python demo\12_mcp_local.py "hello 로 test 해줘"
```

실제 출력:

```
[server] demo-test-tool 시작 (stdio)              ← 자식 프로세스가 stderr 로 남긴 로그
======================================================================
[12] MCP (stdio)   model=qwen3.8-local:27b   host=http://127.0.0.1:11434
질의: 안녕하세요 라는 문자열로 test 도구를 실행하고 결과를 알려줘.
======================================================================
(MCP 서버는 이 파일이 자식 프로세스로 자동 기동합니다)
[mcp] list_tools -> ['test']                      ← 11번에는 없던 단계
[1] 도구 호출: test({'a': '안녕하세요'})  <- MCP 경유
123---안녕하세요---456                             ← 자식 프로세스에서 실행됨
[1] 도구 결과: {'ok': True, 'result': '123---안녕하세요---456'}
[2] 도구 호출 없음 -> 종료
----------------------------------------------------------------------
`123---안녕하세요---456`
```

11번과 최종 결과가 같습니다. 다른 것은 `[mcp] list_tools` 한 줄과, `123---...` 을 찍은
주체가 **다른 프로세스**라는 사실뿐입니다.

## 1장. MCP가 뭐고 왜 필요한가

11번에서 도구를 쓰려면 이런 것들이 필요했습니다.

- 도구 함수가 **같은 파이썬 프로세스 안에** 있어야 한다
- 도구 명세(JSON Schema)를 **내 코드에 dict로** 써 둬야 한다
- 그 도구는 **내 프로그램만** 쓸 수 있다

도구가 늘고, 팀이 나뉘고, 다른 언어로 짠 도구를 붙이고 싶어지면 이 구조가 걸립니다.
그리고 도구를 쓰는 쪽이 늘어날 때마다 명세를 복사해야 합니다.

**MCP(Model Context Protocol)** 는 이 지점을 표준화합니다. 한 문장으로:

> 도구를 **별도 프로세스(서버)** 로 떼어 내고, 정해진 프로토콜로 "어떤 도구가 있나(list_tools)"
> 와 "이 도구를 이 인자로 실행해 달라(call_tool)" 를 주고받는다.

얻는 것:

| | 11번 native | 12번 MCP |
|---|---|---|
| 도구 명세 | 내 코드에 하드코딩 | 서버에게 **물어본다** |
| 도구가 도는 곳 | 같은 프로세스 | 별도 프로세스 (격리) |
| 재사용 | 이 프로그램만 | 프로토콜을 아는 **모든** 클라이언트 |
| 언어 | 파이썬끼리만 | 서버가 무슨 언어든 상관없음 |
| 배포 | 코드를 합쳐야 함 | 서버만 갈아끼우면 됨 |

Claude Desktop, IDE 확장, 다른 에이전트 프레임워크가 같은 MCP 서버를 그대로 붙여 쓸 수 있는
것이 이 표준의 실익입니다.

### stdio와 JSON-RPC

이 파일이 쓰는 트랜스포트는 **stdio** 입니다. 클라이언트가 서버를 자식 프로세스로 띄우고,
그 프로세스의 **표준입력/표준출력 파이프**로 대화합니다.

```
클라이언트 ──(stdin 에 JSON 한 줄 씀)──▶ 서버
클라이언트 ◀─(stdout 에 JSON 한 줄 씀)── 서버
```

오가는 메시지 형식은 **JSON-RPC** 입니다. 대략 이런 모양입니다.

```json
{"jsonrpc":"2.0","id":2,"method":"tools/call",
 "params":{"name":"test","arguments":{"a":"hello"}}}
```

여기서 아주 중요한 결론이 나옵니다. **서버의 stdout은 프로토콜 전용 통로입니다.**
서버 코드에서 `print()` 를 하면 그 문자열이 JSON 사이에 끼어들어 대화가 깨집니다.
5장에서 이 문제를 실제로 다룹니다.

## 2장. 한 파일이 서버이자 클라이언트

보통 MCP 예제는 서버 파일과 클라이언트 파일이 따로입니다. 이 예제는 **한 파일로 실행**
하는 것이 목표라 두 역할을 한 파일에 담고 인자로 갈랐습니다.

```python
async def main() -> None:
    argv = sys.argv[1:]

    if "--server" in argv:
        await serve()  # 서버 모드
        return

    ...
    answer = await run_client(query)  # 클라이언트 모드
```

그리고 클라이언트는 **자기 자신**을 서버로 띄웁니다.

```python
return StdioServerParameters(
    command=sys.executable,  # 지금 돌고 있는 python.exe
    args=[str(Path(__file__).resolve()), "--server"],  # 이 파일 + --server
    env=env,
)
```

그림으로:

```
python 12_mcp_local.py
        │
        │  (클라이언트 모드로 진입)
        │
        └─ spawn ─▶  python 12_mcp_local.py --server     (서버 모드로 진입)
                            ▲                    │
                    stdin(요청)              stdout(응답)
                            │                    ▼
                     ───────── JSON-RPC 파이프 ─────────
```

- `sys.executable` — 현재 실행 중인 파이썬 인터프리터의 절대경로. 가상환경(`.venv`)에서
  돌고 있다면 자식도 같은 가상환경을 쓰게 되어 패키지가 어긋나지 않습니다.
- `Path(__file__).resolve()` — 이 파일의 절대경로. 상대경로로 넘기면 자식의 작업 디렉터리가
  다를 때 파일을 못 찾습니다. Windows 경로는 문자열 조립 대신 `pathlib` 로 다룹니다.
- `env.setdefault("PYTHONIOENCODING", "utf-8")` — 자식 프로세스의 한글 깨짐 방지.
  `setdefault` 는 "이미 값이 있으면 그대로, 없을 때만 설정"입니다.

## 4장. 서버 (1) — `on_list_tools`

```python
async def on_list_tools(
    ctx: ServerRequestContext, params: types.PaginatedRequestParams | None
) -> types.ListToolsResult:
    return types.ListToolsResult(
        tools=[
            types.Tool(
                name=TOOL_NAME,
                description=TOOL_DESCRIPTION,
                input_schema=TOOL_INPUT_SCHEMA,
            )
        ]
    )
```

클라이언트가 "너 무슨 도구 갖고 있어?" 하고 물으면 답하는 핸들러입니다.
11번에서 코드에 박아 뒀던 명세가 여기서는 **응답 데이터**가 됩니다. 이것이 MCP의 첫 번째
변화입니다 — 클라이언트는 도구를 미리 알 필요가 없습니다.

### SDK 버전 주의 (중요)

이 저장소에 설치된 MCP 파이썬 SDK는 **2.x** 이고, 웹에 흔한 1.x 예제와 API가 다릅니다.
1.x 코드를 붙여넣으면 동작하지 않습니다.

| | 1.x | 2.x (이 코드) |
|---|---|---|
| 핸들러 등록 | `@server.list_tools()` 데코레이터 | `Server(on_list_tools=...)` 콜백 |
| 스키마 필드 | `inputSchema=` (카멜케이스) | `input_schema=` (스네이크케이스) |
| 반환 타입 | `list[Tool]` | `ListToolsResult` |
| 클라이언트 | `stdio_client()` + `ClientSession` | `Client(StdioServerParameters(...))` |

`input_schema` 를 `inputSchema` 로 쓰면 바로 에러가 나므로 금방 알아챌 수 있습니다.

`ctx` 와 `params` 는 이 예제에서 쓰지 않지만 시그니처는 맞춰야 합니다. SDK가 이 형태로
호출하기 때문입니다.

## 5장. 서버 (2) — `on_call_tool` 과 stdout 금지 규칙

```python
async def on_call_tool(
    ctx: ServerRequestContext, params: types.CallToolRequestParams
) -> types.CallToolResult:
    args = dict(params.arguments or {})

    if params.name != TOOL_NAME:
        payload = {"ok": False, "error": f"알 수 없는 도구입니다: {params.name}"}
    else:
        a = args.get("a")
        if not isinstance(a, str) or not a:
            payload = {"ok": False, "error": "인자 a 는 비어 있지 않은 문자열이어야 합니다."}
        else:
            with contextlib.redirect_stdout(sys.stderr):
                payload = {"ok": True, "result": test(a)}

    return types.CallToolResult(
        content=[types.TextContent(type="text", text=json.dumps(payload, ensure_ascii=False))]
    )
```

검증 로직은 11번 `call_tool()` 과 **같습니다.** 달라진 껍데기만 보면 됩니다.

### (1) `redirect_stdout` — 이 파일에서 가장 중요한 세 줄

```python
with contextlib.redirect_stdout(sys.stderr):
    payload = {"ok": True, "result": test(a)}
```

`test()` 안에는 `print(f"{res}")` 가 있습니다. 1장에서 봤듯 **stdio 서버의 stdout은
JSON-RPC 전용 통로**입니다. 이 print가 그대로 나가면 서버가 보내는 JSON 사이에
`123---hello---456` 이라는 날문자열이 끼어들어 클라이언트의 파싱이 깨집니다.

증상은 대개 이렇게 나타나서 원인을 짐작하기 어렵습니다.

```
ValidationError / JSONDecodeError / 그냥 멈춤
```

`contextlib.redirect_stdout(sys.stderr)` 는 **그 블록 안에서만** `print()` 의 목적지를
stderr로 바꿉니다. stderr는 프로토콜과 무관하므로 안전하고, 사용자 화면에는 그대로 보입니다.
0장 출력에서 `123---안녕하세요---456` 이 보이는 것도 이 경로 덕분입니다.

> 규칙으로 외우면 됩니다. **stdio MCP 서버 코드 경로에서 `print()` 금지.**
> 로그는 `logging`(기본 stderr)이나 `print(..., file=sys.stderr)` 로 남깁니다.
> 13번(HTTP)에는 이 제약이 없습니다 — 그 대비가 [13_코드설명.md](13_코드설명.md) 의 주제입니다.

### (2) 실패를 `is_error` 로 보내지 않는 이유

MCP의 `CallToolResult` 에는 `is_error` 필드가 있지만 **쓰지 않습니다.**
도구 실패는 11번과 똑같이 `{"ok": false, "error": ...}` 라는 **본문 데이터**로 보냅니다.

이유는 11번 6장과 같습니다. 이 값의 독자는 LLM이고, LLM이 읽고 스스로 고쳐 재시도할 수
있어야 합니다. `is_error` 를 쓰면 클라이언트 SDK 계층에서 예외로 바뀌어 모델에게 닿기 전에
흐름이 끊길 수 있습니다. **11번과 12번의 동작이 정확히 같아야 한다**는 것이 이 예제의
존재 이유이므로, 실패 표현 방식도 같아야 합니다.

### (3) 결과는 텍스트 콘텐츠로

```python
return types.CallToolResult(
    content=[types.TextContent(type="text", text=json.dumps(payload, ensure_ascii=False))]
)
```

MCP는 결과를 **콘텐츠 목록**으로 돌려줍니다(텍스트, 이미지 등). 우리는 dict를 JSON 문자열로
직렬화해 텍스트 하나로 보냅니다. 받는 쪽에서 다시 `json.loads` 로 되돌립니다(8장).

**여기가 11번과 실질적으로 다른 지점입니다.** 11번은 dict가 함수 반환값으로 그대로
건너왔지만, 12번은 `dict → JSON 문자열 → 파이프 → JSON 문자열 → dict` 라는 **직렬화 경계**를
지납니다. 그래서 도구 반환값은 반드시 JSON으로 표현 가능한 값이어야 합니다.
파이썬 객체, `datetime`, 집합 같은 것을 그대로 넣으면 여기서 터집니다.

## 6장. 서버 조립과 `serve()`

```python
server = Server(
    SERVER_NAME,
    version="0.1.0",
    title="문자열 test 도구",
    instructions="문자열 앞뒤에 표식을 붙이는 도구 하나만 제공합니다.",
    on_list_tools=on_list_tools,
    on_call_tool=on_call_tool,
)
```

앞의 두 핸들러를 꽂아 서버 객체를 만듭니다. `instructions` 는 클라이언트가 초기화 때 받는
서버 전체 안내문으로, 도구 개별 설명과는 다릅니다.

```python
async def serve() -> None:
    print(f"[server] {SERVER_NAME} 시작 (stdio)", file=sys.stderr)
    async with stdio_server() as (read_stream, write_stream):
        await server.run(read_stream, write_stream, server.create_initialization_options())
```

- `file=sys.stderr` — 5장의 규칙을 여기서도 지킵니다. 서버 기동 로그조차 stdout에 쓰면 안 됩니다.
- `stdio_server()` 는 `async with` 로 쓰는 **비동기 컨텍스트 매니저**입니다. 진입할 때
  stdin/stdout을 읽기/쓰기 스트림으로 감싸 주고, 빠져나올 때 정리합니다.
- `server.run(...)` 은 클라이언트가 연결을 끊을 때까지 돌며 요청을 처리합니다.
  즉 이 `await` 는 **서버 수명 내내 기다립니다.**

## 7장. 클라이언트 (1) — 서버를 띄우고 붙기

```python
async with Client(server_params()) as mcp:
    listed = await mcp.list_tools()
    schemas = to_ollama_schemas(listed.tools)
```

`Client(...)` 에 진입하는 순간 세 가지가 한꺼번에 일어납니다.

1. 자식 프로세스(서버) 기동
2. 초기화 핸드셰이크 (프로토콜 버전, 서버 정보 교환)
3. 세션 준비 완료

그리고 `async with` 를 빠져나가면 **자식 프로세스까지 정리됩니다.** 별도의 종료 코드를
쓰지 않아도 되는 이유입니다. `with` 문의 역할이 "쓰고 나면 반드시 치운다"라는 걸 기억하면
됩니다 — 파일 객체를 `with open(...)` 으로 여는 것과 같은 원리입니다.

`await mcp.list_tools()` 가 4장의 핸들러를 원격 호출합니다. 이 한 줄이 11번에는 없던
단계이고, 도구 명세가 코드가 아니라 **런타임 응답**이 됐다는 증거입니다.

## 8장. 클라이언트 (2) — 스키마 번역과 `call_tool`

### MCP Tool → Ollama 스키마

MCP의 도구 형식과 Ollama가 요구하는 function calling 형식은 모양이 다릅니다. 번역이 필요합니다.

```python
def to_ollama_schemas(mcp_tools) -> list[dict[str, Any]]:
    return [
        {
            "type": "function",
            "function": {
                "name": t.name,
                "description": t.description or "",
                "parameters": t.input_schema or {"type": "object", "properties": {}},
            },
        }
        for t in mcp_tools
    ]
```

이 번역을 거치고 나면 **모델에게 보내는 `tools` 배열은 11번의 `TOOL_SCHEMA` 와 사실상
같아집니다.** 3장에서 세 조각으로 흩어졌던 이름/설명/스키마가 여기서 다시 하나로 합쳐집니다.

이것이 이 예제의 핵심 주장입니다.

> **모델은 MCP를 쓰는지 모릅니다.** 모델이 보는 것은 어느 쪽이든 같은 tools 배열입니다.
> MCP는 모델 바깥, 우리 코드와 도구 사이의 문제입니다.

### 실행 위임

```python
async def call_tool(name: str, arguments: dict[str, Any]) -> dict[str, Any]:
    try:
        response = await mcp.call_tool(name, arguments)
    except Exception as exc:
        return {"ok": False, "error": f"MCP 호출 실패: {type(exc).__name__}: {exc}"}
    text = first_text(response)
    if text is None:
        return {"ok": False, "error": "MCP 응답에 텍스트 콘텐츠가 없습니다."}
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        return {"ok": True, "text": text}
```

11번에서는 이 함수가 `test(a)` 를 직접 불렀습니다. 여기서는 **심부름을 보냅니다.**
시그니처(이름, 인자 dict를 받아 dict를 반환)는 그대로라서 에이전트 루프는 차이를 모릅니다.

방어가 세 겹인 데 주목하세요. 통신은 함수 호출보다 실패할 구석이 많습니다.

1. `except Exception` — 서버가 죽었거나 파이프가 끊긴 경우. **여기서도 예외를 던지지 않고**
   dict로 바꿔 모델에게 넘깁니다.
2. `first_text(response) is None` — 응답에 텍스트 콘텐츠가 없는 경우.
3. `except json.JSONDecodeError` — JSON이 아닌 텍스트가 온 경우. 버리지 않고
   `{"ok": True, "text": ...}` 로 살려 둡니다. 남의 MCP 서버는 JSON을 안 줄 수도 있습니다.

`first_text()` 는 콘텐츠 목록에서 첫 번째 텍스트를 꺼내는 도우미입니다.

```python
def first_text(response) -> str | None:
    for item in getattr(response, "content", None) or []:
        if getattr(item, "type", None) == "text":
            return item.text
    return None
```

`getattr(..., None) or []` 패턴이 반복되는 이유는 11번 8장과 같습니다 — **없을 수도 있는
속성을 안전하게 읽고, `None` 을 빈 리스트로 바꿔 반복문이 그냥 0회 돌게** 하기 위해서입니다.

### 그 아래 에이전트 루프

`run_client()` 의 나머지(240줄 이후)는 11번 `run_agent()` 와 **구조가 같습니다.**
messages를 만들고, `chat()` 하고, `tool_calls` 가 없으면 종료하고, 있으면 실행해서
`role: "tool"` 로 되돌립니다. 여기 설명을 반복하지 않겠습니다 —
[11_코드설명.md 8장](11_코드설명.md#8장-run_agent--대화가-자라는-과정) 을 그대로 읽으면 됩니다.

**그 사실 자체가 이 예제의 결론입니다.** 트랜스포트를 바꿔도 에이전트 루프는 손대지 않습니다.

## 9장. 11번과 나란히 놓고 보기

| | 11 native | 12 MCP stdio |
|---|---|---|
| 도구 명세 | 코드의 `TOOL_SCHEMA` dict | `await mcp.list_tools()` 응답 |
| 도구 실행 | `test(a)` 직접 호출 | `await mcp.call_tool(...)` 프로토콜 왕복 |
| 실행 프로세스 | 같은 프로세스 | 자식 프로세스 |
| 데이터 경계 | dict 그대로 | dict → JSON → 파이프 → JSON → dict |
| `print()` | 자유 | **서버 쪽 금지** (redirect 필요) |
| 실패 전달 | `{"ok": false}` | `{"ok": false}` — **같음** |
| 에이전트 루프 | — 같음 — | |
| 모델이 보는 tools | — 같음 — | |
| 최종 결과 | — 같음 — | |

바뀐 것은 전부 "도구를 어떻게 조달하는가"이고, 바뀌지 않은 것은 전부 "무엇을 하는가"입니다.
이 경계가 MCP를 이해하는 요점입니다.

### 실험해 보기

**실험 1 — stdout 금지 규칙을 어겨 본다**

`with contextlib.redirect_stdout(sys.stderr):` 줄을 지우고(그리고 아래 줄의 들여쓰기를
한 단계 줄이고) 실행해 보세요. 프로토콜이 깨지는 모습을 직접 보면 5장이 규칙이 아니라
현상으로 이해됩니다.

**실험 2 — 서버만 따로 띄워 본다**

```powershell
python demo\12_mcp_local.py --server
```

아무 반응 없이 멈춘 것처럼 보입니다. **정상입니다.** stdin으로 JSON-RPC가 들어오기를
기다리는 중입니다. `Ctrl+C` 로 끄면 됩니다. 서버가 "웹서버처럼 화면에 뭔가 뿌리는 것"이
아니라는 감을 잡는 데 좋습니다.

**실험 3 — 도구를 하나 더 추가한다**

`on_list_tools` 에 `types.Tool(...)` 을 하나 더 넣고 `on_call_tool` 에 분기를 추가하세요.
클라이언트 코드는 **한 줄도 고치지 않아도** 새 도구가 모델에게 노출됩니다.
`[mcp] list_tools -> [...]` 출력이 늘어나는 것으로 확인할 수 있습니다.
