# 코드 설명 — 이 저장소의 Tool Calling과 MCP를 하나씩 뜯어보기

이 문서는 **파이썬을 막 시작했고 AI 에이전트 개발은 처음인 사람**을 대상으로 합니다.
이 저장소의 코드를 위에서 아래로 따라가며, "왜 이렇게 짰는가"까지 설명합니다.

읽고 나면 다음을 할 수 있게 되는 것이 목표입니다.

1. LLM이 도구를 호출한다는 말이 **실제로 무슨 일**인지 설명할 수 있다
2. 파이썬 함수 하나를 LLM이 쓸 수 있는 도구로 바꿀 수 있다
3. 같은 도구를 MCP 서버로 노출하고 클라이언트로 불러올 수 있다
4. 안 될 때 어디를 봐야 하는지 안다

> **먼저 알아둘 것**
> 이 저장소의 주제는 "기차 예약 기능"이 아니라 **도구를 어떻게 설계하고 연동하는가**입니다.
> 기차 예약은 여러 단계에 걸쳐 상태가 이어지는 소재라서 예제로 골랐을 뿐입니다.

## 0장. 시작하기 전에

### 0.1 이 저장소가 하는 일

사용자가 이렇게 입력합니다.

```
내일 오전 9시 서울에서 부산 가는 기차 예약해줘.
```

그러면 로컬에서 도는 LLM이 스스로 판단해서, 브라우저를 열고, 조회하고, 열차를 고르고,
예약자 정보를 넣고, 좌석을 확보한 뒤 예약번호를 알려줍니다. **사람이 순서를 짜 주지
않습니다.** 무엇을 언제 부를지는 모델이 정합니다.

그리고 **같은 도구 집합을 두 가지 경로로** 연결해 둔 것이 이 저장소의 핵심입니다.

| | Phase 1 | Phase 2 |
|---|---|---|
| 이름 | Native tool calling | MCP (Model Context Protocol) |
| 진입점 | [`agent_tools.py`](../src/toolsdemo/agent_tools.py) | [`mcp_/client_agent.py`](../src/toolsdemo/mcp_/client_agent.py) |
| 도구를 어떻게 얻는가 | 내 프로세스 안의 목록에서 바로 | 별도 서버 프로세스에 물어봐서 |
| 도구를 어떻게 실행하는가 | 함수를 그냥 호출 | 서버에 "이거 실행해줘"라고 메시지를 보내서 |

**도구 구현 코드는 한 벌뿐입니다.** Phase 1과 Phase 2는 그것을 감싸는 얇은 껍데기입니다.

### 0.2 실행 방법 (문서를 따라가며 직접 돌려보려면)

터미널 두 개가 필요합니다. 셸은 PowerShell 기준입니다.

```powershell

python -m toolsdemo.mcp_.client_agent "내일 오전 9시 서울에서 부산 가는 기차 예약해줘"
```

Phase 2 는 MCP 서버와 **HTTP** 로도 대화할 수 있습니다. 그때는 터미널이 하나 더 필요합니다(13장).

> mock 사이트는 **별도 프로세스**입니다. 에이전트가 알아서 띄워 주지 않습니다.
> 이걸 잊으면 `ERR_CONNECTION_REFUSED`가 납니다. 16장에서 다시 다룹니다.

## 1장. 오해부터 풀기 — LLM은 함수를 실행하지 못한다

에이전트를 처음 배울 때 가장 큰 오해가 이것입니다.

> ❌ "LLM에게 함수를 등록해 두면 LLM이 그 함수를 실행한다"

**아닙니다.** LLM이 할 수 있는 일은 오직 하나, **텍스트를 생성하는 것**뿐입니다.
파일을 읽지도, 브라우저를 열지도, 인터넷에 접속하지도 못합니다.

그럼 "tool calling"은 뭘까요? 이렇게 생각하면 정확합니다.

> ✅ LLM은 **"이 함수를 이런 인자로 부르고 싶다"는 내용의 JSON을 출력**할 뿐이고,
> 그 JSON을 읽고 **실제로 함수를 실행하는 것은 우리가 짠 파이썬 코드**입니다.
> 실행 결과를 다시 대화에 넣어 주면 모델이 그걸 읽고 다음 판단을 합니다.

### 1.1 한 번의 왕복

```
① 우리 코드 → 모델
   "사용자가 이렇게 말했어. 그리고 네가 쓸 수 있는 함수 목록은 이거야."
   (사용자 메시지 + tools 배열)

② 모델 → 우리 코드
   "search_trains 를 {departure:'서울', arrival:'부산', date:'2026-08-30'} 로 부르고 싶어."
   (tool_calls)

③ 우리 코드
   실제로 search_trains(...) 를 실행한다. 브라우저가 움직이는 건 이 순간.

④ 우리 코드 → 모델
   "결과는 이거야: {ok:true, count:22, options:[...]}"
   (role="tool" 메시지를 대화에 추가)

⑤ 모델 → 우리 코드
   "그럼 다음은 select_train 을 부를게." → ②로 돌아감
   또는 "예약 끝났어, 예약번호는 R34708865야." → 종료
```

②~⑤를 **모델이 더 이상 도구를 부르지 않을 때까지 반복**하는 것이 에이전트 루프이고,
이 저장소에서는 [`llm/ollama_client.py`](../src/toolsdemo/llm/ollama_client.py)의
`OllamaAgent.run()` 이 그 반복문입니다. 6장에서 한 줄씩 봅니다.

### 1.2 그래서 우리가 짜야 하는 것은 세 가지

| 짜야 하는 것 | 이 저장소의 위치 | 설명하는 장 |
|---|---|---|
| ① 실제로 일하는 함수 (도구) | `tools/booking.py` | 3장, 8장 |
| ② 그 함수를 모델이 이해할 형식으로 설명하는 명세 | `tools/registry.py` 가 자동 생성 | 4·5장 |
| ③ ②를 넘기고 ①을 실행해 결과를 되먹이는 반복문 | `llm/ollama_client.py` | 6장 |

MCP(9장 이후)는 이 중 **②와 ①을 다른 프로세스로 옮기는 표준 방법**입니다.
③은 그대로입니다. 이게 이 저장소가 보여주려는 전부입니다.

## 2장. 이 코드를 읽기 위한 파이썬 최소 지식

이 저장소는 초보자에게 낯선 문법을 네 가지 씁니다. 여기만 알면 나머지는 평범한 파이썬입니다.

### 2.1 `async def` 와 `await` — 기다리는 동안 놀지 않기

브라우저 조작은 "클릭하고 페이지가 뜰 때까지 기다리기"의 연속입니다. 그냥 기다리면 그 시간에
아무 일도 못 합니다. `async`/`await` 는 **기다리는 동안 다른 일을 할 수 있게** 해 줍니다.

```python
async def search_trains(...):        # async 가 붙은 함수 = 코루틴 함수
    page = await get_page()          # await = "이거 끝날 때까지 기다려" (그동안 양보)
    options = await _adapter.search(page, ...)
```

기억할 규칙 세 가지입니다.

1. `async def` 로 만든 함수는 **그냥 부르면 실행되지 않습니다.** `await` 를 붙여야 합니다.
   `search_trains(...)` 만 쓰면 "코루틴 객체"라는 실행 예약표만 생기고 끝납니다.
2. `await` 는 **`async def` 안에서만** 쓸 수 있습니다.
3. 최상위에서 시작할 때는 `asyncio.run(...)` 을 씁니다.
   [`agent_tools.py`](../src/toolsdemo/agent_tools.py)의 마지막이 바로 그것입니다.

```python
def main() -> None:  # 평범한 함수
    setup_logging()
    query = " ".join(sys.argv[1:]).strip() or DEFAULT_QUERY
    sys.exit(asyncio.run(run(query)))  # 여기서 async 세계로 진입
```

> **이 저장소의 규칙:** 도구 함수는 **반드시** `async def` 입니다.
> 아니면 등록 단계에서 바로 거절당합니다 (4장).

### 2.2 데코레이터 — 함수 위에 붙는 `@`

```python
@tool
async def get_today() -> dict[str, Any]: ...
```

`@tool` 은 마법이 아닙니다. 아래 두 줄과 **완전히 같은 뜻**입니다.

```python
async def get_today() -> dict[str, Any]: ...


get_today = tool(get_today)  # ← 함수를 tool() 에 넣고, 그 반환값을 다시 이름에 붙인다
```

즉 `tool` 은 **함수를 인자로 받는 함수**입니다. 이 저장소의 `tool()` 은 함수를 받아서
(1) 검사하고 (2) 명세를 만들어 목록에 저장한 뒤 (3) **원래 함수를 그대로 돌려줍니다.**
그래서 `get_today()` 를 직접 부르면 평소처럼 동작합니다. 등록만 곁다리로 일어난 것입니다.

### 2.3 타입 힌트 — 주석이 아니라 데이터

```python
async def fill_passenger(name: str, phone: str = "", passengers: int = 1) -> dict[str, Any]:
```

`name: str` 은 "name 은 문자열"이라는 표시입니다. 파이썬은 이걸 강제하지 않지만
(문자열 아닌 걸 넣어도 에러가 안 납니다), **프로그램이 읽어볼 수 있는 정보**로 남습니다.
이 저장소는 그 점을 이용해 타입 힌트를 **JSON Schema로 자동 번역**합니다 (4장).

- `phone: str = ""` 처럼 `=` 로 기본값이 있으면 → **선택 인자**
- 기본값이 없으면 → **필수 인자**

이 구분이 그대로 모델에게 전달됩니다.

### 2.4 dict 와 JSON — 같은 모양, 다른 세계

```python
{"ok": True, "today": "2026-08-29"}  # 파이썬 dict
{"ok": true, "today": "2026-08-29"}  # JSON 텍스트 (True → true)
```

파이썬 `dict` 는 메모리 안의 객체이고, JSON은 **글자로 적힌 문자열**입니다.
프로세스 사이로 데이터를 보내려면 글자로 바꿔야 합니다.

```python
json.dumps(파이썬_dict, ensure_ascii=False)  # dict → JSON 문자열 (직렬화)
json.loads(json_문자열)  # JSON 문자열 → dict (역직렬화)
```

`ensure_ascii=False` 는 한글을 `서울` 같은 형태가 아니라 `서울` 그대로 쓰라는 뜻입니다.
이 저장소는 로그와 MCP 전송 양쪽에서 이 옵션을 씁니다.

> **왜 중요한가:** Phase 1은 dict를 그대로 주고받지만, Phase 2(MCP)는 프로세스가 달라서
> **반드시 JSON 문자열로 바뀌었다가 되돌아옵니다.** 그래서 도구 반환값은 "JSON으로 바꿀 수
> 있는 값"만 담아야 합니다. 파이썬 객체를 그대로 넣으면 MCP 경로에서 깨집니다.

### 2.5 도구 시그니처 한 줄 정독 — `async def get_today() -> dict[str, Any]:`

앞의 네 절을 합치면 이 한 줄이 완전히 읽힙니다. 실제 도구의 첫 줄이니 부위별로 나눠 봅니다.

```
async def   get_today   ()      -> dict[str, Any]   :
  (1)         (2)       (3)            (4)         (5)
```

(1) 비동기 함수 선언 · (2) 함수 이름(= 모델이 부를 도구 이름) · (3) 인자 없음 ·
(4) **반환 타입 힌트** · (5) 본문 시작

#### (1) `async def` — "부르면 실행된다"가 깨지는 지점

보통 함수는 부르면 그 자리에서 실행됩니다. `async def` 는 다릅니다. 직접 확인해 보세요.

```python
import asyncio
from toolsdemo.tools import booking

print(booking.get_today())  # await 없이
print(asyncio.run(booking.get_today()))  # await 하고
```

실제 출력입니다.

```
<coroutine object get_today at 0x000002126D36C120>
{'ok': True, 'today': '2026-08-29', 'weekday': '토', 'tomorrow': '2026-08-30'}
sys:1: RuntimeWarning: coroutine 'get_today' was never awaited
```

- `get_today()` 라고만 쓰면 함수 본문이 **한 줄도 실행되지 않고**,
  "실행 예약표"에 해당하는 **코루틴 객체**가 나옵니다.
- `await` 를 붙여야 본문이 돌고 dict가 나옵니다.
- 실행되지 않은 채 버려지면 `coroutine ... was never awaited` 경고가 뜹니다.
  **이 경고를 보면 `await` 를 빠뜨린 것**입니다.

```python
result = get_today()  # 코루틴 객체. result["today"] 하면 TypeError
result = await get_today()  # dict
```

#### (4) `-> dict[str, Any]` 는 무엇을 가리키는 화살표인가

여기가 가장 헷갈리는 부분입니다.

> `->` 뒤의 타입은 **`await` 를 끝낸 뒤 손에 쥐는 값**의 타입입니다.
> 함수를 부른 **직후**에 나오는 코루틴 객체를 가리키는 것이 아닙니다.

```python
coro = get_today()  # 타입: coroutine        ← 힌트가 말하는 대상이 아님
val = await get_today()  # 타입: dict[str, Any]   ← 힌트가 말하는 대상
```

엄밀히는 호출식의 타입이 `Coroutine[Any, Any, dict[str, Any]]` 이지만,
`async def` 에서는 **관례적으로 `await` 결과만 적습니다.**
`-> Coroutine[...]` 이라고 쓰면 오히려 잘못된 표기가 됩니다.

#### `dict[str, Any]` 읽는 법

```
dict [ str , Any ]
       키    값
```

"**키는 문자열, 값은 아무 타입이나 되는 딕셔너리**"입니다. 실제 반환값을 보면 이유가 보입니다.

```python
{
    "ok": True,  # bool
    "today": "2026-08-29",  # str
    "weekday": "토",  # str
    "tomorrow": "2026-08-30",  # str
}
```

- **키가 `str` 인 이유** — 이 dict는 곧 `json.dumps()` 로 JSON이 되어 모델에게 갑니다.
  JSON 객체의 키는 문자열만 가능합니다(2.4절).
- **값이 `Any` 인 이유** — `bool`, `str`, `int`, `list` 가 섞입니다. 도구마다 반환 항목이
  달라 하나로 묶을 수 없습니다. `Any` 는 "여기서는 타입을 좁히지 않겠다"는 선언입니다.

`Any` 는 표준 라이브러리에서 가져옵니다.

```python
from typing import Any
```

> **버전 메모:** 파이썬 3.9부터 소문자 `dict[str, Any]` 를 쓸 수 있습니다. 그 전에는
> `from typing import Dict` 후 `Dict[str, Any]` 였습니다. 인터넷 예제에 대문자 `Dict` 가
> 보이면 옛 문법입니다. 이 저장소는 3.10 기준이라 소문자를 씁니다.

#### 타입 힌트는 강제되지 않는다 — 그런데 이 저장소는 읽는다

```python
async def get_today() -> dict[str, Any]:
    return "안녕하세요"  # 문자열을 돌려줘도 파이썬은 에러를 내지 않는다
```

파이썬은 실행 중에 타입 힌트를 검사하지 않습니다. 힌트는 **사람과 도구를 위한 메모**이고,
에디터 자동완성이나 `ruff` 같은 검사 도구가 읽습니다.

다만 이 저장소에서는 `registry.py` 가 힌트를 **직접 읽어 JSON Schema를 만듭니다**(4장).
그런데 확인해 보면 이렇습니다.

```python
>>> typing.get_type_hints(booking.get_today)
{'return': dict[str, typing.Any]}

>>> get_registry()["get_today"].parameters
{'type': 'object', 'properties': {}, 'required': []}
```

- 파이썬은 `return` 힌트를 분명히 기억하고 있습니다.
- 그런데 생성된 스키마에는 **반환 타입 정보가 전혀 없습니다.**
  (`properties` 가 빈 것은 `get_today` 에 인자가 없기 때문입니다.)

즉 **스키마로 바뀌는 것은 인자 힌트뿐이고, `-> dict[str, Any]` 는 쓰이지 않습니다.**
모델에게 "이 도구가 무엇을 돌려주는지" 알려주는 것은 타입 힌트가 아니라
**docstring의 `Returns:` 문장**입니다.

```python
    """오늘 날짜와 요일을 알려준다. ...

    Returns:
        today: 오늘 날짜 (YYYY-MM-DD), weekday: 요일, tomorrow: 내일 날짜
    """
```

반환 힌트를 아무리 정교하게 써도 모델의 행동은 바뀌지 않습니다.
**모델을 움직이려면 docstring을 고쳐야 합니다.**

#### 초보자가 자주 하는 실수 3가지

| 실수 | 증상 | 고치는 법 |
|---|---|---|
| `await` 를 안 붙임 | `coroutine ... was never awaited` 경고, `TypeError: 'coroutine' object is not subscriptable` | `await` 추가 |
| 일반 함수 안에서 `await` 사용 | `SyntaxError: 'await' outside async function` | 감싸는 함수를 `async def` 로 바꾸거나 `asyncio.run()` 사용 |
| "async면 알아서 빨라진다"고 기대 | 아무 변화 없음 | `async` 는 **기다리는 시간에 양보**할 뿐입니다. 계산 자체를 빠르게 하지 않습니다 |

#### 한 줄 요약

| 표기 | 뜻 |
|---|---|
| `async def` | 코루틴 함수. 그냥 부르면 예약표만 나오고, `await` 해야 실행됨 |
| `()` | 인자 없음 → 모델도 인자 없이 호출 (`get_today({})`) |
| `-> dict[str, Any]` | **`await` 결과**가 "문자열 키 + 아무 값" 딕셔너리라는 표시 |
| 강제력 | 런타임에는 없음. 단 이 저장소는 **인자** 힌트를 읽어 스키마를 만듦 (반환 힌트는 사용 안 함) |

## 3장. 도구 한 개를 뜯어본다 — `get_today`

가장 단순한 도구부터 봅니다. [`tools/booking.py`](../src/toolsdemo/tools/booking.py)에 있습니다.

```python
@tool
async def get_today() -> dict[str, Any]:
    """오늘 날짜와 요일을 알려준다. '내일', '이번 주말' 같은 표현을 날짜로 바꿀 때 먼저 호출한다.

    Returns:
        today: 오늘 날짜 (YYYY-MM-DD), weekday: 요일, tomorrow: 내일 날짜
    """
    today = date_cls.today()
    weekdays = ["월", "화", "수", "목", "금", "토", "일"]
    return {
        "ok": True,
        "today": today.isoformat(),
        "weekday": weekdays[today.weekday()],
        "tomorrow": (today + timedelta(days=1)).isoformat(),
    }
```

함수 자체는 초보자도 읽을 수 있는 평범한 코드입니다. 중요한 건 **세 가지 약속**입니다.

### 약속 1 — `async def` 로 만든다

브라우저를 안 쓰는 `get_today` 조차 `async` 입니다. 왜일까요?
**호출하는 쪽이 모든 도구를 똑같이 다루기 위해서**입니다. 루프는 `await 도구(...)` 한 줄로
모든 도구를 부릅니다. 어떤 건 async고 어떤 건 아니면 부르는 쪽이 매번 분기해야 합니다.

### 약속 2 — 항상 dict를 반환한다. 예외를 던지지 않는다

성공이든 실패든 dict입니다.

```python
{"ok": True,  "today": "2026-08-29", ...}
{"ok": False, "error": "날짜 형식이 잘못되었습니다: '내일모레'. YYYY-MM-DD 로 주세요."}
```

**왜 예외를 던지지 않을까요?** 예외를 던지면 프로그램이 거기서 멈춥니다. 하지만 우리는
**모델이 실패를 읽고 스스로 고쳐서 다시 시도하기를** 바랍니다. 그러려면 실패가 프로그램의
사고가 아니라 **모델에게 보여줄 데이터**여야 합니다. 실제로 이렇게 동작합니다.

```
[tool] ← search_trains: {'ok': False, 'error': "날짜 형식이 잘못되었습니다 ... YYYY-MM-DD 로 주세요."}
→ 모델이 이 문장을 읽고, 날짜를 고쳐서 search_trains 를 다시 호출한다
```

에러 메시지를 **모델에게 주는 지시문처럼** 쓰는 것이 요령입니다.
"잘못됨"이 아니라 "YYYY-MM-DD 로 주세요", "search_trains 를 먼저 호출하세요"처럼
**다음에 뭘 하면 되는지**를 적습니다.

### 약속 3 — docstring이 곧 프롬프트다

이게 초보자가 가장 놓치기 쉬운 부분입니다.

> **모델이 이 도구에 대해 아는 정보는 docstring이 전부입니다.**
> 함수 본문은 모델에게 보이지 않습니다. 변수 이름도, 주석도 안 보입니다.

그래서 docstring에 이런 것들이 들어 있습니다.

- **언제 쓰는지**: "'내일', '이번 주말' 같은 표현을 날짜로 바꿀 때 **먼저** 호출한다"
- **순서 제약**: "예약의 첫 단계이며 반드시 가장 먼저 호출한다" (`search_trains`)
- **형식**: "반드시 YYYY-MM-DD 형식" (`date` 인자)
- **하지 말아야 할 것**: "결제를 수행하는 도구는 존재하지 않으니 찾지 마세요" (`confirm_booking`)

모델이 도구를 안 부르거나 인자를 틀리면, 시스템 프롬프트가 아니라 **docstring부터**
의심하세요. 이 저장소의 규칙이기도 합니다.

## 4장. `@tool` 데코레이터 — 파이썬 함수가 JSON Schema가 되기까지

파일: [`tools/registry.py`](../src/toolsdemo/tools/registry.py)

### 4.1 문제 상황

모델에게 도구를 알려주려면 **JSON Schema**라는 형식으로 명세를 줘야 합니다. 손으로 쓰면
이렇게 생겼습니다.

```json
{
  "type": "object",
  "properties": {
    "departure": {"type": "string", "description": "출발역 이름. 예: 서울"},
    "arrival":   {"type": "string", "description": "도착역 이름. 예: 부산"}
  },
  "required": ["departure", "arrival"]
}
```

도구가 7개면 이걸 7번 씁니다. 그리고 함수 시그니처를 고칠 때마다 **두 곳을 같이** 고쳐야
합니다. 안 고치면 모델은 없는 인자를 보내고, 있는 인자를 모르게 됩니다.
이런 어긋남은 조용히 생기고 디버깅이 어렵습니다.

**그래서 이 저장소는 JSON Schema를 손으로 쓰지 않습니다.** 함수의 타입 힌트와 docstring에
이미 같은 정보가 있으니, 그걸 읽어서 자동으로 만듭니다.

### 4.2 `tool()` 이 하는 일 — 전체 4단계

```python
def tool(fn: ToolFn) -> ToolFn:
    """async 함수를 도구로 등록하는 데코레이터."""
    if not inspect.iscoroutinefunction(fn):  # (1) 검사
        raise TypeError(f"도구 {fn.__name__} 는 async 함수여야 합니다.")

    description, parameters = _build_schema(fn)  # (2) 명세 생성
    spec = ToolSpec(name=fn.__name__, description=description, parameters=parameters, fn=fn)
    if spec.name in _REGISTRY:  # (3) 중복 이름 방지
        raise ValueError(f"도구 이름 중복: {spec.name}")
    _REGISTRY[spec.name] = spec  # (4) 목록에 저장
    return fn  # 원래 함수 그대로 반환
```

- **(1)** `async def` 가 아니면 즉시 에러. 규칙을 문서가 아니라 코드로 강제합니다.
- **(2)** 핵심. 4.4절에서 자세히 봅니다.
- **(3)** 이름은 모델이 도구를 지목하는 유일한 열쇠라 겹치면 안 됩니다.
- **(4)** `_REGISTRY` 는 그냥 모듈 전역 `dict` 입니다. `{"get_today": ToolSpec(...), ...}`

`ToolSpec` 은 도구 하나에 대한 정보 묶음입니다.

```python
@dataclass(frozen=True)
class ToolSpec:
    name: str  # 함수 이름 그대로
    description: str  # docstring 요약 → 모델이 읽음
    parameters: dict[str, Any]  # JSON Schema  → 모델이 읽음
    fn: ToolFn  # 실제 함수    → 우리가 실행할 때 씀
```

앞의 세 개는 **모델에게 보여주는 얼굴**이고, 마지막 `fn` 은 **우리만 쓰는 실행 손잡이**입니다.
이 구분이 뒤에 MCP를 이해할 때 그대로 쓰입니다. MCP 서버는 앞의 세 개만 네트워크로
건네주고, `fn` 은 서버 프로세스 안에 남습니다.

> **`frozen=True` 는 무슨 뜻인가요?** 한 번 만들면 값을 바꿀 수 없는 객체라는 뜻입니다.
> 도구 명세가 실행 도중 바뀌면 모델에게 보여준 것과 실제가 달라지므로 아예 막습니다.

### 4.3 등록은 "언제" 일어나는가 — import의 부수효과

초보자가 자주 헷갈리는 지점입니다. `@tool` 이 붙은 코드는 **그 파일을 import하는 순간**
실행됩니다. 그래서 진입점에 이런 줄이 있습니다.

```python
from .tools import booking  # noqa: F401 - import 시점에 도구가 registry 에 등록된다
```

`booking` 이라는 이름을 코드에서 한 번도 쓰지 않는데 import합니다. 이상해 보이지만
**import 자체가 목적**입니다. 이 줄이 없으면 `_REGISTRY` 는 비어 있고, 모델에게 넘길
도구가 0개가 됩니다. (`# noqa: F401` 은 "안 쓰는 import라고 경고하지 마"라는 표시입니다.)

Phase 1 진입점과 MCP 서버 **양쪽 모두** 이 줄을 갖고 있습니다. 도구를 채워 넣는 방식이
같아야 두 경로가 같은 도구 집합을 보게 되기 때문입니다.

### 4.4 `_build_schema()` — 시그니처와 docstring 읽기

```python
def _build_schema(fn: ToolFn) -> tuple:
    sig = inspect.signature(fn)  # 인자 목록과 기본값
    try:
        hints = typing.get_type_hints(fn)  # 인자 타입
    except Exception:
        hints = {}

    summary, arg_docs = _split_docstring(fn.__doc__ or "")
    if not summary:
        raise ValueError(
            f"도구 {fn.__name__} 에 docstring 요약이 없습니다. docstring 이 곧 프롬프트입니다."
        )
```

- `inspect.signature(fn)` — 함수를 **밖에서 들여다보는** 표준 도구입니다.
  인자 이름, 순서, 기본값을 알려줍니다.
- `typing.get_type_hints(fn)` — 타입 힌트를 실제 타입 객체로 가져옵니다.
- **docstring 요약이 없으면 등록 자체를 거부합니다.** 설명 없는 도구는 모델에게 쓸모가
  없으니, 만들 수조차 없게 막은 것입니다.

이어서 인자를 하나씩 돌며 스키마를 조립합니다.

```python
for name, param in sig.parameters.items():
    schema = _json_type(hints.get(name, param.annotation))  # 타입 → {"type": "..."}
    desc = arg_docs.get(name)
    if desc:
        schema["description"] = desc  # docstring Args 설명 붙이기
    if param.default is not inspect.Parameter.empty:
        schema["default"] = param.default  # 기본값 있으면 선택 인자
    else:
        required.append(name)  # 없으면 필수 인자
    properties[name] = schema

parameters = {"type": "object", "properties": properties, "required": required}
```

정리하면 이런 대응입니다.

| 파이썬 코드 | JSON Schema로 변환된 결과 |
|---|---|
| `departure: str` | `"departure": {"type": "string"}` + `required` 에 추가 |
| `passengers: int = 1` | `"passengers": {"type": "integer", "default": 1}` (required 아님) |
| docstring의 `departure: 출발역 이름. 예: 서울` | 위 항목에 `"description": "출발역 이름. 예: 서울"` |

`_json_type()` 이 타입 변환표입니다. `str→string`, `int→integer`, `float→number`,
`bool→boolean`, `list→array`, `dict→object`. `str | None` 같은 형태는 `None` 을 빼고
남은 타입을 씁니다. 모르는 타입은 안전하게 `string` 으로 떨어집니다.

### 4.5 docstring 쪼개기 — `_split_docstring()`

Google 스타일 docstring을 정규식으로 자릅니다.

```python
parts = re.split(r"^\s*(?:Args|Arguments|Params|Parameters)\s*:\s*$", doc, flags=re.M)
summary = parts[0].strip()  # Args: 앞부분 = 도구 설명
```

`Args:` 줄을 기준으로 앞을 **도구 설명**, 뒤를 **인자별 설명**으로 나눕니다.
인자 설명 쪽은 `이름: 설명` 패턴을 찾아 모으고, 줄바꿈으로 이어진 설명은 앞 항목에 붙입니다.
`Returns:` 같은 다음 섹션을 만나면 거기서 멈춥니다.

> **직접 확인한 동작:** 이 규칙 때문에 `Args:` 섹션이 **없는** 도구는 `Returns:` 블록까지
> 설명에 그대로 남습니다. 실제로 `get_today` 의 최종 description은
> 요약문 + `Returns: ...` 전체이고, `Args:` 가 있는 `search_trains` 는 그 앞의 한 줄만
> 설명이 됩니다. 모델에게 반환값 설명이 함께 보이는 것 자체는 해롭지 않지만,
> **"내가 쓴 docstring이 정확히 어떻게 잘려서 모델에게 가는지"는 눈으로 확인**하세요.

확인 방법은 간단합니다. 아래를 그대로 실행하면 실제 생성된 명세를 볼 수 있습니다.

```python
import json
from toolsdemo.tools import booking  # ← 이 import가 등록을 일으킨다
from toolsdemo.tools.registry import get_registry

spec = get_registry()["search_trains"]
print(spec.description)
print(json.dumps(spec.parameters, ensure_ascii=False, indent=2))
```

### 4.6 실제 생성 결과

위 코드를 돌리면 `search_trains` 에 대해 이런 결과가 나옵니다.
**손으로 쓴 JSON이 아니라 함수에서 자동 생성된 것**입니다.

```json
{
  "type": "object",
  "properties": {
    "departure":    {"type": "string", "description": "출발역 이름. 예: 서울"},
    "arrival":      {"type": "string", "description": "도착역 이름. 예: 부산"},
    "date":         {"type": "string", "description": "출발 날짜. 반드시 YYYY-MM-DD 형식. 모르면 get_today 를 먼저 호출한다."},
    "depart_after": {"type": "string", "description": "이 시각 이후 열차만 조회. HH:MM 형식(24시간제). 예: 09:00. 비우면 전체.", "default": ""}
  },
  "required": ["departure", "arrival", "date"]
}
```

원본 함수와 나란히 놓고 보세요.

```python
async def search_trains(
    departure: str, arrival: str, date: str, depart_after: str = ""
) -> dict[str, Any]:
    """출발역/도착역/날짜로 기차를 조회한다. 예약의 첫 단계이며 반드시 가장 먼저 호출한다.

    Args:
        departure: 출발역 이름. 예: 서울
        arrival: 도착역 이름. 예: 부산
        date: 출발 날짜. 반드시 YYYY-MM-DD 형식. 모르면 get_today 를 먼저 호출한다.
        depart_after: 이 시각 이후 열차만 조회. HH:MM 형식(24시간제). 예: 09:00. 비우면 전체.
    """
```

- 인자 이름 → `properties` 의 키
- 타입 힌트 → `"type"`
- docstring `Args:` 의 각 줄 → `"description"`
- `= ""` 가 있는 `depart_after` 만 `required` 에서 빠지고 `default` 가 붙음

**고칠 곳이 한 군데뿐입니다.** 함수 시그니처를 바꾸면 명세가 따라옵니다. 어긋날 수가 없습니다.

## 5장. 모델에게 실제로 보내는 것 — `tools` 배열

Ollama(그리고 OpenAI 호환 API 대부분)는 도구 목록을 이런 모양으로 받습니다.

```python
def ollama_tool_schemas() -> list[dict[str, Any]]:
    """Ollama function calling 용 tools 배열."""
    return [
        {
            "type": "function",
            "function": {
                "name": spec.name,
                "description": spec.description,
                "parameters": spec.parameters,
            },
        }
        for spec in _REGISTRY.values()
    ]
```

`ToolSpec` 을 API가 요구하는 껍데기에 담는 것뿐입니다. 실제 결과 하나는 이렇습니다.

```json
{
  "type": "function",
  "function": {
    "name": "fill_passenger",
    "description": "예약자 정보를 입력한다. 아직 확정되지 않으며 confirm_booking 을 호출해야 예약이 끝난다.\n\n사이트에 따라 이 단계가 없을 수 있으며, 그때는 skipped:true 로 응답합니다.",
    "parameters": {
      "type": "object",
      "properties": {
        "name":       {"type": "string",  "description": "예약자 이름"},
        "phone":      {"type": "string",  "description": "연락처. 예: 010-1234-5678. 모르면 비워 둔다.", "default": ""},
        "passengers": {"type": "integer", "description": "탑승 인원 수. 기본 1명.", "default": 1}
      },
      "required": ["name"]
    }
  }
}
```

이 배열이 **매 요청마다** 모델에게 함께 전달됩니다. 모델은 이걸 읽고
"지금 상황에는 `fill_passenger` 가 맞겠다. `name` 은 필수니까 채워야 하고,
`phone` 은 몰라도 되는구나" 하고 판단합니다.

> **비용 감각:** 도구 설명은 매 요청에 전부 들어갑니다. 도구가 많고 설명이 길수록
> 컨텍스트를 먹고 느려집니다. 그렇다고 짧게 줄이면 모델이 잘못 씁니다.
> "필요한 만큼 정확하게, 그 이상은 쓰지 않기"가 요령입니다.
> 이 저장소가 도구를 7개로 유지하는 것도 같은 이유입니다.

여기까지가 **"모델에게 무엇을 줄 것인가"** 였습니다. 이제 그것을 실제로 주고받는
반복문을 봅니다.

## 6장. 에이전트 루프 — 대화가 자라는 과정

파일: [`llm/ollama_client.py`](../src/toolsdemo/llm/ollama_client.py)

이 파일이 에이전트의 심장입니다. **Phase 1과 Phase 2가 이 파일을 그대로 공유합니다.**

### 6.1 핵심 아이디어 — `messages` 라는 하나의 리스트

LLM API는 상태가 없습니다. 지난 대화를 기억하지 못합니다.
그래서 **매번 대화 전체를 다시 보냅니다.** 에이전트란 결국
"이 리스트에 메시지를 계속 덧붙이면서 다시 물어보는 반복문"입니다.

처음에는 두 개로 시작합니다.

```python
messages = [
    {"role": "system", "content": self.system_prompt},  # 규칙
    {"role": "user", "content": user_message},  # 사용자 질의
]
```

한 번 돌 때마다 이렇게 자랍니다.

| 순서 | role | 내용 | 누가 만들었나 |
|---|---|---|---|
| 1 | `system` | 규칙 ("반드시 도구를 호출해라", "결제하지 마라" …) | 우리 |
| 2 | `user` | "내일 오전 9시 서울에서 부산 …" | 사용자 |
| 3 | `assistant` | (내용 없음) + `tool_calls: [get_today]` | **모델** |
| 4 | `tool` | `{"ok": true, "today": "2026-08-29", ...}` | **우리 코드가 실행한 결과** |
| 5 | `assistant` | (내용 없음) + `tool_calls: [search_trains]` | 모델 |
| 6 | `tool` | `{"ok": true, "count": 22, "options": [...]}` | 우리 |
| … | … | … | … |
| 끝 | `assistant` | "예약이 완료되었습니다. 예약번호는 …" (`tool_calls` 없음) | 모델 |

**`tool_calls` 가 없는 `assistant` 메시지가 나오면 끝**입니다. 모델이 "더 부를 도구가 없다,
이제 사람에게 답하겠다"고 말한 것이기 때문입니다. 이 한 줄이 종료 조건 전부입니다.

### 6.2 루프 본체

```python
for step in range(1, settings.max_tool_iterations + 1):
    response = await self._chat(messages)          # (1) 모델에게 현재 대화 전체를 보냄
    message = response.message
    tool_calls = getattr(message, "tool_calls", None) or []

    assistant_msg = {"role": "assistant", "content": message.content or ""}
    if tool_calls:
        assistant_msg["tool_calls"] = [
            {"function": {"name": tc.function.name, "arguments": tc.function.arguments}}
            for tc in tool_calls
        ]
    messages.append(assistant_msg)                 # (2) 모델의 답을 대화에 기록

    if not tool_calls:                             # (3) 도구를 안 불렀으면 종료
        return AgentResult(answer=(message.content or "").strip(), ...)

    for tc in tool_calls:                          # (4) 부른 도구를 하나씩 실행
        name = tc.function.name
        args = tc.function.arguments
        if isinstance(args, str):                  # 모델이 문자열로 줄 때가 있다
            try:
                args = json.loads(args)
            except json.JSONDecodeError:
                args = {}
        result = await self.tool_caller(name, dict(args or {}))    # ★ 실행
        messages.append({                          # (5) 결과를 대화에 추가
            "role": "tool",
            "name": name,
            "tool_name": name,
            "content": json.dumps(result, ensure_ascii=False, default=str),
        })
```

한 단계씩 짚어봅니다.

**(1) 모델 호출.** `messages` 전체를 매번 다시 보냅니다. 대화가 길어질수록 보내는 양도
늘어납니다. 이게 정상입니다.

**(2) 모델의 답을 반드시 기록.** 초보자가 자주 빠뜨리는 부분입니다. 모델이 "도구를 부르겠다"고
말한 사실 자체를 대화에 남겨야, 다음 차례에 온 `tool` 결과가 **무엇에 대한 답인지** 짝이
맞습니다. 이 줄을 빼면 모델이 같은 도구를 계속 다시 부르는 무한 루프에 빠지기 쉽습니다.

**(3) 종료 조건.** 6.1에서 설명한 그것입니다.

**(4) 인자가 문자열로 올 수 있다.** 모델에 따라 `arguments` 를 dict로 주기도 하고
`'{"departure": "서울"}'` 같은 **문자열**로 주기도 합니다. 그래서 문자열이면 `json.loads`
로 풀고, 그것마저 실패하면 빈 dict로 둡니다. **여기서 예외를 던지지 않는 게 중요합니다.**
모델이 이상한 걸 뱉었다고 프로그램이 죽으면 안 됩니다.

**(5) 결과를 JSON 문자열로 넣는다.** `role: "tool"` 메시지의 `content` 는 문자열이어야
하므로 `json.dumps` 로 바꿉니다.
- `ensure_ascii=False` → 한글이 그대로 보입니다 (모델도 사람도 읽기 쉬움).
- `default=str` → JSON으로 못 바꾸는 값이 섞여 있어도 문자열로 우겨넣어 **죽지 않게** 합니다.

### 6.3 `tool_caller` — 이 한 줄이 Phase 1과 2를 가른다

```python
result = await self.tool_caller(name, dict(args or {}))
```

`self.tool_caller` 는 생성자에서 받은 함수입니다. 루프는 **그게 뭔지 모릅니다.**
이름과 인자를 주면 dict를 돌려주는 무언가, 그게 전부입니다.

```python
# Phase 1 — agent_tools.py
agent = OllamaAgent(tool_schemas=ollama_tool_schemas(), tool_caller=call_tool)
#                                                       ↑ 같은 프로세스의 함수

# Phase 2 — mcp_/client_agent.py
agent = OllamaAgent(tool_schemas=schemas, tool_caller=caller)
#                                          ↑ MCP 서버에 심부름 보내는 함수
```

**이 설계 덕분에 MCP를 붙이면서 루프를 한 줄도 고치지 않았습니다.**
"바뀔 수 있는 부분을 밖에서 주입한다"는 흔한 설계 원칙의 아주 실용적인 사례입니다.

### 6.4 모델 호출 설정

```python
kwargs = {
    "model": settings.ollama_model,
    "messages": messages,
    "tools": self.tool_schemas,  # 5장에서 만든 그 배열
    "options": {"temperature": 0},
}
try:
    return await self.client.chat(think=settings.think, **kwargs)
except TypeError:
    return await self.client.chat(**kwargs)  # 구버전 라이브러리는 think 를 모른다
```

- **`temperature=0`** — 모델의 무작위성을 끕니다. 소설을 쓰는 게 아니라 인자를 정확히
  뽑아내는 작업이라 창의성이 필요 없습니다. 같은 질의에 같은 결과가 나오게 하는 효과도 있습니다.
- **`think`** — qwen3.6 같은 모델은 답하기 전에 "생각"을 길게 출력하는 기능이 기본으로
  켜져 있습니다. 도구 호출만 시킬 때는 느려지기만 해서 기본을 끕니다(`THINK=false`).
- **`try/except TypeError`** — 라이브러리 버전에 따라 `think` 인자를 모를 수 있어,
  거절당하면 빼고 다시 부릅니다.

### 6.5 무한 루프 방지

```python

    ...
logger.warning("MAX_TOOL_ITERATIONS(%d) 도달 — 루프 중단", settings.max_tool_iterations)
```

모델이 같은 도구를 계속 부르며 끝내지 않을 수 있습니다. 상한(기본 8회)을 두고,

**스크립트가 실패했음을 알 수 있게** 합니다.

> **에이전트를 만들 때 반드시 넣어야 하는 안전장치입니다.** 상한이 없으면 모델이 헤매는
> 동안 브라우저가 계속 움직이고 토큰이 계속 소모됩니다.

### 6.6 시스템 프롬프트는 무엇을 담는가

```python
SYSTEM_PROMPT = """당신은 기차 예약을 대신 처리하는 에이전트입니다.
...
2. 예약 순서는 search_trains → select_train → fill_passenger → confirm_booking 입니다.

7. 도구가 ok:false 를 돌려주면 error 메시지를 읽고 스스로 고쳐서 다시 시도하세요.
8. 결제를 시도하지 마세요. 결제 도구는 존재하지 않습니다.
"""
```

여기서 배울 점은 **역할 분담**입니다.

| 어디에 쓰나 | 무엇을 쓰나 |
|---|---|
| 도구 docstring | 그 도구 하나에 대한 사용법 (인자 형식, 언제 쓰는지) |
| 시스템 프롬프트 | 도구 **사이의** 관계와 작업 전체의 규칙 (순서, 금지, 답변 형식) |

도구 하나로 설명되는 내용을 시스템 프롬프트에 쓰면, 도구를 지울 때 프롬프트에 유령이
남습니다. 반대로 도구 사이의 순서를 docstring에만 쓰면 모델이 전체 그림을 못 봅니다.

## 7장. `call_tool` — 실패를 예외가 아니라 데이터로

Phase 1에서 도구를 실제로 실행하는 함수입니다.
파일: [`tools/registry.py`](../src/toolsdemo/tools/registry.py)

```python
async def call_tool(name: str, arguments: dict[str, Any]) -> dict[str, Any]:
    """도구를 실행한다. **예외를 던지지 않고** 항상 dict 를 반환한다."""
    spec = _REGISTRY.get(name)
    if spec is None:  # (1) 없는 도구
        return {"ok": False, "error": f"알 수 없는 도구: {name}", "available": list(_REGISTRY)}

    arguments = arguments or {}
    logger.info("[tool] → %s(%s)", name, arguments)  # (2) 호출 로그
    try:
        allowed = set(spec.parameters["properties"])  # (3) 미정의 인자 걸러내기
        cleaned = {k: v for k, v in arguments.items() if k in allowed}
        dropped = set(arguments) - allowed
        if dropped:
            logger.warning("[tool] %s: 미정의 인자 무시 %s", name, sorted(dropped))
        result = await spec.fn(**cleaned)  # (4) 실제 실행
    except TypeError as exc:  # (5) 인자가 안 맞을 때
        result = {"ok": False, "error": f"인자 오류: {exc}", "expected": spec.parameters}
    except Exception as exc:  # (6) 그 밖의 모든 사고
        logger.exception("[tool] %s 실행 실패", name)
        result = {"ok": False, "error": f"{type(exc).__name__}: {exc}"}

    logger.info("[tool] ← %s: %s", name, result)  # (7) 응답 로그
    return result
```

### (1) 없는 도구를 부를 때 — `available` 을 함께 준다

모델이 도구 이름을 틀리게 지어내는 일이 실제로 있습니다. 그때 "알 수 없는 도구"라고만
하면 모델은 뭘 부를 수 있는지 모릅니다. **쓸 수 있는 목록을 같이 돌려주면 스스로 고칩니다.**

### (3) 스키마에 없는 인자를 걸러낸다 — 실전에서 꼭 필요한 방어

모델은 스키마에 없는 인자를 만들어 보냅니다. 예를 들어
`search_trains(departure, arrival, date, train_type="KTX")` 처럼, 그럴싸하지만 정의되지
않은 `train_type` 을 붙입니다. 그대로 `fn(**arguments)` 를 하면 `TypeError` 가 나며 죽습니다.

그래서 **정의된 인자만 남기고 나머지는 버립니다.** 버린 사실은 경고 로그로 남깁니다
(같은 경고가 반복되면 docstring이 부족하다는 신호입니다).

> **왜 도구마다 방어하지 않고 여기서 한 번만 할까요?**
> 도구가 7개면 같은 방어를 7번 써야 하고, 새 도구를 만들 때마다 빠뜨릴 수 있습니다.
> **모든 호출이 반드시 지나가는 길목**에서 한 번 막는 것이 훨씬 안전합니다.
> 이런 자리를 찾는 눈이 곧 설계 감각입니다.

### (5)(6) 어떤 사고가 나도 dict로 돌려준다

`except Exception` 은 보통 나쁜 습관으로 배웁니다. 여기서는 **의도된 선택**입니다.
도구 안에서 무슨 일이 나든(브라우저 타임아웃, 셀렉터 못 찾음, 사이트 접속 실패)
**루프는 계속 돌아야** 하고, 모델은 그 실패를 읽고 판단해야 하기 때문입니다.

- `logger.exception(...)` — 사람을 위해 전체 스택 트레이스를 로그에 남깁니다.
- `return {"ok": False, ...}` — 모델을 위해 짧은 요약을 돌려줍니다.

**사람이 볼 것과 모델이 볼 것을 나눠 놓은 것**이 포인트입니다.

### (2)(7) 호출과 응답을 항상 INFO로 남긴다

```
14:44:41 INFO  [tool] → get_today({})
14:44:41 INFO  [tool] ← get_today: {'ok': True, 'today': '2026-08-29', ...}
```

디버깅에서 가장 먼저 보게 되는 줄입니다. 에이전트가 이상하게 굴 때
"모델이 뭘 부르려 했는가 / 도구가 뭘 돌려줬는가"만 알면 원인의 절반은 잡힙니다.

이 저장소는 **화살표 방향**으로 둘을 구분합니다. `→` 는 요청, `←` 는 응답입니다.

## 8장. 상태를 가진 도구들 — 예약 흐름과 브라우저

지금까지는 도구 한 개가 독립적으로 동작하는 이야기였습니다. 그런데 실제 예약은
**앞 단계의 결과 위에서** 다음 단계가 돌아갑니다. 조회를 안 했으면 고를 수 없고,
고르지 않았으면 확정할 수 없습니다. 이게 진짜 어려운 부분입니다.

### 8.1 순서가 있는 도구 — 모듈 전역 `_state`

파일: [`tools/booking.py`](../src/toolsdemo/tools/booking.py)

```python
#: 마지막 조회 컨텍스트. 다단계 흐름에서 LLM 이 인자를 다시 안 줘도 되게 한다.
_state: dict[str, Any] = {"last_query": None, "options": [], "selected": None}
```

`search_trains` 가 성공하면 결과를 여기에 담아 둡니다.

```python
_state["options"] = options
_state["selected"] = None
```

그리고 다음 도구들은 **시작하자마자 전제를 확인**합니다.

```python
async def select_train(train_no: str) -> dict[str, Any]:
    if not _state["options"]:
        return {"ok": False, "error": "조회 결과가 없습니다. search_trains 를 먼저 호출하세요."}

async def fill_passenger(name: str, ...) -> dict[str, Any]:
    if not _state["selected"]:
        return {"ok": False, "error": "선택된 열차가 없습니다. select_train 을 먼저 호출하세요."}

async def confirm_booking() -> dict[str, Any]:
    if not _state["selected"]:
        return {"ok": False, "error": "선택된 열차가 없습니다. select_train 을 먼저 호출하세요."}
```

**여기서 핵심은 에러 메시지의 문장입니다.** "잘못된 상태입니다"가 아니라
**"search_trains 를 먼저 호출하세요"** 라고 씁니다. 모델은 이 문장을 읽고 실제로
그 도구를 먼저 부릅니다. 즉 **에러 메시지가 모델에게 주는 다음 지시**입니다.

> 순서를 프롬프트로만 강제하면 모델이 어길 때 막을 방법이 없습니다.
> 도구 안에서 전제를 확인하면, 어겨도 **복구 방법과 함께 되돌려줄 수 있습니다.**

### 8.2 입력 검증 사다리 — `search_trains`

```python
if not departure.strip() or not arrival.strip():
    return {
        "ok": False,
        "error": "출발역과 도착역은 비울 수 없습니다.",
        "hint": "예: departure='서울', arrival='부산'",
    }
if departure.strip() == arrival.strip():
    return {"ok": False, "error": f"출발역과 도착역이 같습니다: {departure!r}"}

day = _normalize_date(date)
if day is None:
    return {
        "ok": False,
        "error": f"날짜 형식이 잘못되었습니다: {date!r}. YYYY-MM-DD 로 주세요.",
        "hint": "get_today 를 호출해 오늘 날짜를 확인한 뒤 계산하세요.",
    }
if depart_after and not _TIME_RE.match(depart_after.strip()):
    return {"ok": False, "error": f"시각 형식이 잘못되었습니다: {depart_after!r}. HH:MM 로 주세요."}
```

브라우저를 건드리기 **전에** 값부터 검사합니다. 이유는 두 가지입니다.

1. 브라우저 조작은 느립니다. 어차피 실패할 일을 5초 기다린 뒤 실패시킬 이유가 없습니다.
2. 실패 원인이 명확해집니다. "폼 입력 실패" 대신 "날짜 형식이 잘못됨"이라고 말할 수 있습니다.

`_normalize_date` 는 관대함도 갖췄습니다. `YYYY-MM-DD` 면 그대로 쓰고,
`오늘`/`내일`/`모레` 같은 표현은 계산해 줍니다. 그 외는 거절합니다.

```python
def _normalize_date(value: str) -> str | None:
    if _DATE_RE.match(value):
        return value
    relative = {"오늘": 0, "내일": 1, "모레": 2}
    if value in relative:
        return (date_cls.today() + timedelta(days=relative[value])).isoformat()
    return None
```

> **받을 때는 너그럽게, 돌려줄 때는 엄격하게.** 모델의 출력은 완벽하지 않으니 흔한 변형은
> 받아 주되, 우리가 사이트에 넣는 값은 항상 정확한 형식이어야 합니다.

### 8.3 자르되 잘랐다고 말하기 — 조용한 손실 금지

조회 결과가 22편인데 모델에게 12편만 준다고 합시다. 그냥 12개만 주면 모델은
그게 전부인 줄 알고 "밤 열차는 없습니다"라고 **자신 있게 틀린 답**을 합니다.

```python
_MAX_OPTIONS = 12
shown = options[:_MAX_OPTIONS]
truncated = len(options) > len(shown)

if truncated:
    message += (
        f" 조회된 {len(options)}편 중 출발이 이른 {len(shown)}편만 표시했습니다"
        f" (마지막 표시: {shown[-1]['depart_time']}, 실제 막차: {options[-1]['depart_time']})."
        " 더 늦은 열차가 필요하면 depart_after 를 늦춰 다시 조회하세요."
    )

return {
    "ok": True,
    "count": len(options),  # 전체가 몇 편인지
    "returned": len(shown),  # 그중 몇 편을 줬는지
    "truncated": truncated,  # 잘렸는지
    "available_count": len(available),
    "last_depart_time": options[-1]["depart_time"],  # 진짜 막차
    "options": shown,
    "message": message,
}
```

세 가지를 함께 주는 것이 요령입니다.

1. **잘렸다는 사실** (`truncated`)
2. **잘리기 전 진실** (`count`, `last_depart_time`)
3. **회복하는 방법** (`depart_after 를 늦춰 다시 조회하세요`)

> 컨텍스트를 아끼려고 데이터를 줄이는 것은 정상입니다. **줄였다는 사실을 숨기는 것**이
> 문제입니다. 모델은 자기가 받은 것이 전부라고 가정합니다.

### 8.4 브라우저는 하나만 — `browser.py` 싱글턴

파일: [`tools/browser.py`](../src/toolsdemo/tools/browser.py)

```python
class BrowserSession:
    _instance: BrowserSession | None = None  # 프로세스당 딱 하나
    _lock = asyncio.Lock()

    @classmethod
    async def instance(cls) -> BrowserSession:
        async with cls._lock:
            if cls._instance is None:
                cls._instance = BrowserSession()
            return cls._instance

    async def page(self) -> Page:
        if self._page is not None and not self._page.is_closed():
            return self._page  # 이미 있으면 그대로 재사용
        await self._start()  # 없을 때만 새로 띄운다
        return self._page
```

모든 도구는 `page = await get_page()` 로 **같은 페이지**를 얻습니다.

왜 이래야 할까요? `search_trains` 가 조회 결과 페이지를 열어 두고, `select_train` 이
**그 페이지에서** 예매 버튼을 누르기 때문입니다. 도구를 부를 때마다 브라우저를 새로 띄우면
빈 페이지에서 시작하게 되어 흐름이 성립하지 않습니다. 로그인 세션도 마찬가지입니다.

- `asyncio.Lock()` 은 동시에 두 번 만들어지는 것을 막습니다.
- `_start()` 는 한국어 로케일·서울 시간대·1280x900 창으로 Chromium을 띄웁니다.
- `close_browser()` 는 실행이 끝날 때 정리합니다.
  진입점의 `finally` 에 있어서 **중간에 실패해도 반드시 닫힙니다.**

```python
try:
    result = await agent.run(query)
finally:
    await close_browser()
```

셀렉터는 [`sites/mock.py`](../src/toolsdemo/tools/sites/mock.py) 안에만 있습니다.

> 바뀔 때마다 도구를 뜯어고쳐야 하고, 사이트를 하나 더 붙이면 `if mock: ... else: ...` 가
> 온 코드에 번집니다. **"자주 바뀌는 것"과 "잘 안 바뀌는 것"을 파일 단위로 갈라 두면**

Playwright 사용에서도 규칙이 있습니다. `page.get_by_role("button", name="조회하기")`
처럼 **사람이 화면에서 보는 이름**으로 찾는 것을 우선합니다. `div > div:nth-child(3)`
같은 구조 의존 셀렉터는 화면이 조금만 바뀌어도 깨집니다.

### 8.6 하기 싫은 일은 도구를 만들지 않는다

이 저장소의 자동화 범위는 **좌석 확보(예약)까지**입니다. 결제와 발권은 사람이 합니다.

```
조회 → 열차 선택 → 예약자 정보 → 예약 확정(좌석 확보)  │  결제 → 발권
└─────────────── 에이전트가 자동화 ───────────────┘  └── 사람이 직접 ──┘
```

이걸 강제하는 방법이 인상적입니다. **결제 도구를 아예 만들지 않았습니다.**

```python
async def confirm_booking() -> dict[str, Any]:
    """예약을 확정해 좌석을 확보하고 예약번호를 받는다. 마지막 단계이며 한 번만 호출한다.

    이 도구는 **좌석 확보(예약)까지만** 수행합니다. 결제와 발권은 자동화 대상이 아니며
    사람이 직접 진행합니다. 결제를 수행하는 도구는 존재하지 않으니 찾지 마세요.
    """
```

프롬프트로 "결제하지 마"라고 쓰는 것과, **부를 수단 자체를 주지 않는 것**은 다릅니다.
프롬프트는 우회될 수 있지만, 없는 도구는 부를 수 없습니다.
mock 사이트도 같은 경계를 지켜서 완료 화면에 결제 버튼이 없습니다.

> **에이전트 설계의 일반 원칙:** 모델이 하지 않기를 바라는 일이 있다면,
> 먼저 **그 일을 할 수 있는 도구를 주지 않았는지** 확인하세요.
> 능력을 주고 말리는 것보다, 능력을 안 주는 쪽이 훨씬 확실합니다.

## 9장. MCP란 무엇이고 왜 필요한가

여기까지가 Phase 1입니다. 잘 돌아갑니다. 그런데 한 가지 한계가 있습니다.

### 9.1 Phase 1의 한계

우리가 만든 도구 7개는 **이 파이썬 프로세스 안에서만** 존재합니다.

- 다른 프로그램(예: Claude Desktop, 다른 에이전트)에서 쓰려면? 못 씁니다.
- 도구를 다른 언어로 만들고 싶다면? 못 붙입니다.
- 브라우저 자동화가 죽으면? 에이전트 프로세스도 같이 위험합니다.
- 팀에서 도구만 따로 관리하고 싶다면? 에이전트 코드와 붙어 있어서 어렵습니다.

도구를 **밖으로 꺼내 놓고 누구나 같은 방식으로 쓰게** 하려면 약속이 필요합니다.
그 약속이 **MCP(Model Context Protocol)** 입니다.

### 9.2 MCP를 한 문장으로

> **MCP는 "LLM 애플리케이션이 외부 도구·데이터에 연결하는 방식"을 표준화한 프로토콜입니다.**

비유하자면 USB 같은 것입니다. 예전에는 기기마다 전용 케이블이 있었지만, 규격이 생긴 뒤로는
아무 기기나 같은 포트에 꽂습니다. MCP는 도구 쪽에 그 규격을 준 것입니다.
한 번 MCP 서버로 만들어 두면 **MCP를 지원하는 어떤 호스트에도** 그대로 꽂힙니다.

등장인물은 셋입니다.

| 이름 | 역할 | 이 저장소에서 |
|---|---|---|
| **호스트(Host)** | LLM을 굴리는 애플리케이션 | `client_agent.py` (에이전트 루프를 가진 쪽) |
| **클라이언트(Client)** | 서버와 프로토콜로 대화하는 부분 | SDK의 `Client` 객체 |
| **서버(Server)** | 도구를 실제로 제공하는 쪽 | `mcp_/server.py` (별도 프로세스) |

### 9.3 어떻게 대화하나 — stdio와 JSON-RPC

두 프로세스가 대화하려면 통로(트랜스포트)가 필요합니다. MCP는 크게 두 가지를 씁니다.

- **stdio** — 서버를 자식 프로세스로 띄우고 **표준 입출력**으로 주고받습니다.
  같은 컴퓨터에서 돌릴 때 간단합니다. **이 저장소가 쓰는 방식입니다.**
- **HTTP 계열(Streamable HTTP)** — 서버를 미리 띄워 두고 접속합니다. 원격이나 여러
  클라이언트가 붙을 때 씁니다. **이 저장소도 지원합니다 — 13장에서 다룹니다.**

주고받는 메시지 형식은 **JSON-RPC 2.0** 입니다. 어렵지 않습니다.
"어떤 메서드를, 어떤 인자로" 라고 적어 보내면 같은 `id` 를 단 응답이 옵니다.

```jsonc
// 클라이언트 → 서버 : 도구 목록 좀 줘
{"jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {}}

// 서버 → 클라이언트 : 7개 있어
{"jsonrpc": "2.0", "id": 1, "result": {"tools": [{"name": "get_today", ...}, ...]}}

// 클라이언트 → 서버 : search_trains 실행해줘
{"jsonrpc": "2.0", "id": 2, "method": "tools/call",
 "params": {"name": "search_trains", "arguments": {"departure": "서울", ...}}}

// 서버 → 클라이언트 : 결과는 이 텍스트야
{"jsonrpc": "2.0", "id": 2, "result": {"content": [{"type": "text", "text": "{\"ok\": true, ...}"}]}}
```

우리가 이 JSON을 손으로 만들 일은 없습니다. **SDK가 다 해 줍니다.**
하지만 이 그림을 알아야 두 가지가 이해됩니다.

1. **왜 `print()` 를 쓰면 안 되는가** — stdout은 이 JSON 전용 통로입니다.
   서버가 거기에 아무 글자나 찍으면 프로토콜이 깨집니다. 로그는 stderr로만 남깁니다.
2. **왜 결과가 "텍스트"로 오는가** — 프로세스 사이를 건너오려면 글자가 되어야 합니다.
   그래서 dict → JSON 문자열 → (전송) → JSON 문자열 → dict 왕복이 생깁니다.

### 9.4 그래서 무엇이 바뀌는가 (미리 보기)

| | Phase 1 | Phase 2 |
|---|---|---|
| 도구 목록을 얻는 법 | `ollama_tool_schemas()` | `await client.list_tools()` |
| 도구를 실행하는 법 | `await spec.fn(**args)` | `await client.call_tool(name, args)` |
| 프로세스 | 1개 | 2개 (에이전트 + 도구 서버) |
| 브라우저가 뜨는 곳 | 에이전트 프로세스 | **서버 프로세스** |
| 도구 구현 코드 | `tools/booking.py` | **똑같은 파일** |
| 에이전트 루프 | `OllamaAgent` | **똑같은 클래스** |

바뀌는 건 **도구를 조달하는 경로**뿐입니다. 이제 코드로 확인합니다.

## 10장. MCP 서버 코드 읽기

파일: [`mcp_/server.py`](../src/toolsdemo/mcp_/server.py) — 전체 90여 줄입니다.

> **SDK 버전 주의:** 이 저장소는 **MCP Python SDK 2.x** 기준입니다. 인터넷의 1.x 예제
> (`@server.list_tools()` 데코레이터, `inputSchema=`)를 붙여넣으면 동작하지 않습니다.
> 자세한 대조표는 이 장 끝에 있습니다.

### 10.1 서버가 답해야 하는 두 가지 질문

MCP 서버가 도구를 제공하려면 사실상 두 가지만 답하면 됩니다.

1. **"어떤 도구가 있니?"** → `on_list_tools`
2. **"이거 실행해 줘"** → `on_call_tool`

### 10.2 `on_list_tools` — registry를 프로토콜 형식으로 번역

```python
async def on_list_tools(ctx, params) -> types.ListToolsResult:
    tools = [
        types.Tool(
            name=spec.name,
            description=spec.description,
            input_schema=spec.parameters,  # ← 2.x 는 input_schema (1.x 는 inputSchema)
        )
        for spec in get_registry().values()
    ]
    logger.info("[mcp] list_tools → %d개: %s", len(tools), ", ".join(t.name for t in tools))
    return types.ListToolsResult(tools=tools)
```

5장의 `ollama_tool_schemas()` 와 **모양만 다르고 하는 일은 똑같습니다.**
같은 `ToolSpec` 을 이번에는 MCP가 정한 껍데기(`types.Tool`)에 담을 뿐입니다.

```
             ToolSpec (단일 진실 원천)
              /                  \
   Ollama 형식으로 포장        MCP 형식으로 포장
   {"type":"function", ...}    types.Tool(...)
```

**여기서 `fn` 은 넘기지 않습니다.** 함수 객체는 프로세스 밖으로 나갈 수 없습니다.
나가는 것은 이름·설명·스키마, 즉 **"이런 도구가 있다"는 설명서**뿐입니다.
실행은 서버 안에서 일어납니다.

### 10.3 `on_call_tool` — 실행하고 텍스트로 포장

```python
async def on_call_tool(ctx, params) -> types.CallToolResult:
    result = await call_tool(params.name, dict(params.arguments or {}))

    # is_error 를 쓰지 않는 이유: 도구 실패는 {"ok": false, "error": ...} 라는 **데이터**로
    # LLM 에게 전달되어야 하며, 이는 Phase 1 의 동작과 정확히 같아야 합니다.
    return types.CallToolResult(
        content=[
            types.TextContent(type="text", text=json.dumps(result, ensure_ascii=False, default=str))
        ]
    )
```

첫 줄을 보세요. **7장에서 본 그 `call_tool` 을 그대로 부릅니다.**
미정의 인자 걸러내기, 예외를 dict로 바꾸기 같은 방어가 전부 그대로 적용됩니다.
MCP 서버는 그 결과를 JSON 문자열로 만들어 `TextContent` 에 담을 뿐입니다.

**`is_error` 를 쓰지 않는 결정**이 이 파일에서 가장 중요한 설계 판단입니다.
MCP에는 "이 호출은 실패했다"고 표시하는 방법이 있지만, 그걸 쓰면 실패가 **프로토콜 층의
사고**가 되어 클라이언트/SDK가 다르게 처리할 여지가 생깁니다. 그러면 Phase 1과 동작이
달라집니다. 이 저장소는 실패를 **언제나 `{"ok": false, ...}` 페이로드**로만 전달해서
두 경로를 동일하게 유지합니다. 이 규칙은 테스트로 강제됩니다(12.3절).

### 10.4 서버 객체 만들기

```python
server = Server(
    SERVER_NAME,  # "toolsdemo-booking"
    version=__version__,
    title="기차 예약 도구",
    instructions=(
        "기차 조회부터 예약(좌석 확보)까지 수행하는 도구 모음입니다. "
        "결제와 발권은 제공하지 않으며 사람이 직접 진행해야 합니다."
    ),
    on_list_tools=on_list_tools,  # ← 위에서 만든 함수를 콜백으로 등록
    on_call_tool=on_call_tool,
)
```

`instructions` 는 **서버 전체에 대한 설명**입니다. 호스트가 이 서버를 소개할 때 씁니다.
도구 하나하나의 설명(docstring)과는 층이 다릅니다.

### 10.5 실행 — stdio로 대기

```python
async def serve() -> None:
    logger.info("[mcp] %s 시작 (stdio)", SERVER_NAME)
    try:
        async with stdio_server() as (read_stream, write_stream):
            await server.run(read_stream, write_stream, server.create_initialization_options())
    finally:
        await close_browser()
        logger.info("[mcp] %s 종료", SERVER_NAME)
```

- `stdio_server()` 가 표준 입출력을 읽기/쓰기 스트림으로 만들어 줍니다.
- `server.run(...)` 은 요청이 올 때까지 기다리다가 콜백을 부르는 **무한 대기 루프**입니다.
- `finally` 의 `close_browser()` — 서버가 끝나면 브라우저도 정리합니다.
  **Phase 2에서 브라우저는 이 서버 프로세스 안에서 뜹니다.** 서버가 죽으면 브라우저도
  같이 정리되어야 유령 프로세스가 남지 않습니다.

### 10.6 이 파일에서 반드시 지켜야 할 것

```python
주의 1: stdout 은 JSON-RPC 전용입니다. **이 경로에서 print() 를 쓰지 마세요.**
        로그는 logging(stderr)으로만 남깁니다.
```

파일 맨 위 docstring에 적혀 있는 경고입니다. 디버깅한다고 `print("여기까지 왔음")` 한 줄을
넣으면, 그 글자가 JSON-RPC 스트림에 섞여 들어가 **클라이언트가 응답을 해석하지 못합니다.**
증상이 "이유 없이 통신 실패"라 원인 찾기가 특히 어렵습니다.

### 10.7 새 도구를 추가해도 이 파일은 안 고친다

`on_list_tools` 는 `get_registry()` 를 그때그때 읽습니다.
`on_call_tool` 은 이름으로 `call_tool` 에 넘깁니다.
그래서 [`booking.py`](../src/toolsdemo/tools/booking.py)에 `@tool` 함수를 하나 더 쓰면
**MCP 서버에도 자동으로 노출됩니다.** 서버 파일은 손댈 일이 없습니다.

이것이 "registry를 단일 진실 원천으로 둔다"는 설계의 배당금입니다.

### 10.8 SDK 1.x 예제를 붙여넣으면 안 되는 이유

| | 1.x | 2.x (이 저장소) |
|---|---|---|
| 서버 핸들러 | `@server.list_tools()` 데코레이터 | `Server(on_list_tools=..., on_call_tool=...)` |
| Tool 스키마 필드 | `inputSchema=` | `input_schema=` |
| 핸들러 반환 | `list[Tool]` / `list[TextContent]` | `ListToolsResult` / `CallToolResult` |
| 클라이언트 | `stdio_client()` + `ClientSession` | `Client(StdioServerParameters(...))` |

검색으로 찾은 MCP 예제가 안 돌아간다면 **거의 대부분 버전 문제**입니다.

## 11장. MCP 클라이언트 코드 읽기

파일: [`mcp_/client_agent.py`](../src/toolsdemo/mcp_/client_agent.py)

Phase 2의 진입점입니다. Phase 1의 [`agent_tools.py`](../src/toolsdemo/agent_tools.py)와
나란히 놓고 보면 차이가 뚜렷합니다.

### 11.1 서버를 어떻게 띄우나 — `server_params()`

stdio 방식에서는 **클라이언트가 서버를 자식 프로세스로 직접 실행합니다.**
따로 서버를 켜 둘 필요가 없습니다. 그 실행 방법을 적은 것이 이 함수입니다.

```python
def server_params() -> StdioServerParameters:
    env = dict(os.environ)
    src = str(PROJECT_ROOT / "src")
    env["PYTHONPATH"] = src + os.pathsep + env.get("PYTHONPATH", "")  # (2)
    env.setdefault("PYTHONIOENCODING", "utf-8")  # (3)
    return StdioServerParameters(
        command=sys.executable,  # (1) 지금 이 파이썬으로
        args=["-m", "toolsdemo.mcp_.server"],  #     이 모듈을 실행해라
        env=env,
        cwd=str(PROJECT_ROOT),  # (4)
    )
```

- **(1) `sys.executable`** — "지금 나를 돌리고 있는 파이썬"의 실제 경로입니다.
  `"python"` 이라고 쓰면 가상환경 밖의 다른 파이썬이 잡힐 수 있습니다.
  **가상환경을 그대로 물려주는 가장 안전한 방법**입니다.
- **(2) `PYTHONPATH`** — 자식 프로세스가 `toolsdemo` 패키지를 찾을 수 있게 `src` 를 넣습니다.
- **(3) `PYTHONIOENCODING=utf-8`** — Windows에서 특히 중요합니다. 기본 인코딩이 UTF-8이
  아니면 한글이 섞인 JSON이 깨져서 통신이 실패합니다.
- **(4) `cwd`** — 서버가 프로젝트 루트에서 돌게 해서 `.env` 나 상대 경로가 맞아떨어지게 합니다.

### 11.2 접속 — `async with Client(...)`

```python
async with Client(server_params()) as client:
    listed = await client.list_tools()
    ...
```

이 `async with` 블록이 하는 일이 많습니다.

1. 위에서 정한 명령으로 **서버 프로세스를 띄운다**
2. MCP 초기화 절차(서로 버전·능력 교환)를 끝낸다
3. 블록 안에서 `client.list_tools()` / `client.call_tool()` 을 쓸 수 있게 한다
4. **블록을 빠져나가면 서버 프로세스를 정리한다**

`with` 를 쓰는 이유가 4번입니다. 중간에 에러가 나도 서버가 유령으로 남지 않습니다.

### 11.3 도구 목록 받아 형식 바꾸기

```python
def to_ollama_schemas(mcp_tools) -> list[dict[str, Any]]:
    """MCP Tool 목록 → Ollama function calling 스키마."""
    return [
        {
            "type": "function",
            "function": {
                "name": t.name,
                "description": t.description or "",
                "parameters": t.input_schema or {"type": "object", "properties": {}},
            },
        }
        for t in mcp_tools
    ]
```

MCP가 돌려준 `types.Tool` 을 Ollama가 원하는 모양으로 바꿉니다.
**10.2절에서 서버가 포장한 것을 여기서 다시 풀어 다른 상자에 담는 셈**입니다.

- `t.description or ""` / `t.input_schema or {...}` — 값이 없을 때를 대비한 기본값입니다.
  **다른 사람이 만든 MCP 서버**에 붙을 수도 있으니, 우리 서버만 믿지 않습니다.

결과는 Phase 1의 `ollama_tool_schemas()` 와 **완전히 같은 배열**이어야 합니다.
그래야 모델이 두 경로에서 똑같이 행동합니다. 이건 테스트로 검증합니다(12.3절).

### 11.4 도구 실행 — `caller` 클로저

```python
async def caller(name: str, arguments: dict[str, Any]) -> dict[str, Any]:
    try:
        response = await client.call_tool(name, arguments)  # (1) 서버에 요청
    except Exception as exc:
        return {"ok": False, "error": f"MCP 호출 실패: {type(exc).__name__}: {exc}"}  # (2)

    text = _first_text(response)  # (3) 텍스트 꺼내기
    if text is None:
        return {"ok": False, "error": "MCP 응답에 텍스트 콘텐츠가 없습니다."}
    try:
        return json.loads(text)  # (4) JSON → dict
    except json.JSONDecodeError:
        return {"ok": True, "text": text}  # (5) JSON이 아니면 그대로
```

이 함수가 Phase 1의 `call_tool` 자리에 들어갑니다. 하는 일은 **심부름**입니다.

- **(1)** 이름과 인자를 서버로 보냅니다. 실제 실행은 서버 프로세스에서 일어납니다.
- **(2)** 프로토콜 층에서 사고가 나도(서버가 죽었다든지) **예외를 밖으로 던지지 않습니다.**
  7장과 같은 철학입니다. 루프는 계속 돌아야 하고 모델은 실패를 읽어야 합니다.
- **(3)** 응답은 `content` 배열입니다. 그중 `type == "text"` 인 첫 항목을 꺼냅니다.

```python
def _first_text(response) -> Any:
    for item in getattr(response, "content", None) or []:
        if getattr(item, "type", None) == "text":
            return item.text
    return None
```

- **(4)** 그 텍스트는 서버가 `json.dumps` 한 것이므로 `json.loads` 로 되돌리면
  **Phase 1과 똑같은 dict**가 나옵니다. 여기서 왕복이 완성됩니다.

```
서버:      {"ok": True, ...}  --json.dumps-->  '{"ok": true, ...}'
                                                     │ stdio
클라이언트: {"ok": True, ...}  <--json.loads--  '{"ok": true, ...}'
```

- **(5)** JSON이 아닌 텍스트를 주는 서버도 세상에는 있으니, 그 경우 텍스트째 감싸 전달합니다.

### 11.5 나머지는 Phase 1과 같다

```python
agent = OllamaAgent(tool_schemas=schemas, tool_caller=caller)
result = await agent.run(query)
```

6장에서 본 그 클래스, 그 루프입니다. **한 줄도 다르지 않습니다.**

### 12.3 "같다"를 말이 아니라 테스트로 강제한다

파일: [`tests/test_parity.py`](../tests/test_parity.py)

문서에 "두 Phase는 같습니다"라고 써 두면 언젠가 거짓말이 됩니다. 그래서 기계로 검사합니다.

```python
async def test_mcp_exposes_same_tools_as_registry():
    expected = get_registry()

    async with Client(server_params()) as client:  # 진짜 MCP 서버를 띄운다
        listed = await client.list_tools()

    got = {t.name: t for t in listed.tools}

    assert set(got) == set(expected), "registry 와 MCP 노출 도구 집합이 다릅니다"
    for name, spec in expected.items():
        assert got[name].description == spec.description, f"{name}: 설명 불일치"
        assert got[name].input_schema == spec.parameters, f"{name}: 입력 스키마 불일치"
```

도구를 하나 추가했는데 MCP 쪽 노출을 빠뜨렸다면 여기서 깨집니다.
그리고 **모델에게 보이는 최종 배열**까지 같은지도 확인합니다.

```python
    phase1 = {s["function"]["name"]: s for s in ollama_tool_schemas()}
    ...
    phase2 = {s["function"]["name"]: s for s in to_ollama_schemas(listed.tools)}
```

10.3절에서 말한 "실패는 데이터로" 규칙도 테스트가 지킵니다.

```powershell

```

> **배울 점:** 지켜야 할 설계 원칙이 있으면 문서에 적는 데서 그치지 말고
> **깨지면 빨간 불이 들어오게** 만들어 두세요. 문서는 어겨도 조용하지만 테스트는 소리를 냅니다.

### 12.4 그래서 MCP를 왜 쓰나 (이 데모 규모에서는 Phase 1이 더 단순한데)

솔직히 말해 **이 정도 규모에서는 Phase 1이 더 간단합니다.** 프로세스도 하나고 디버깅도 쉽습니다.
MCP의 값어치는 다른 데서 나옵니다.

| 얻는 것 | 설명 |
|---|---|
| **재사용** | 같은 서버를 MCP를 지원하는 다른 호스트에 그대로 꽂을 수 있습니다. Phase 1 도구는 이 파이썬 프로세스 전용입니다. |
| **프로세스 격리** | 브라우저 자동화가 죽어도 에이전트는 살아 있습니다. |
| **언어 독립** | 서버를 다른 언어로 다시 짜도 클라이언트는 그대로입니다. |
| **명세된 계약** | 도구 발견·호출 방식이 표준이라, 호스트가 처음 보는 서버도 다룰 수 있습니다. |

치르는 비용도 분명합니다. **프로세스 하나 추가, 직렬화 오버헤드, 로그가 두 곳으로 나뉨.**
로그가 나뉜다는 점은 디버깅할 때 체감이 큽니다. 클라이언트 로그에는 `[mcp]` 줄이,
서버 로그(stderr)에는 `[tool]` 줄이 나옵니다.

## 13장. 트랜스포트 바꾸기 — 같은 MCP 서버를 HTTP로

10~12장에서 본 MCP 서버는 **stdio**로 대화했습니다. 그런데 MCP는 트랜스포트를 갈아끼울 수
있게 설계되어 있습니다. 이 저장소는 같은 서버를 **Streamable HTTP**로도 띄울 수 있습니다.

```powershell
python -m toolsdemo.mcp_.http_server      # http://127.0.0.1:8931/mcp
```

이 장의 결론을 먼저 말하면 이렇습니다.

> 도구도, 핸들러도, 에이전트 루프도 그대로입니다.
> **바뀌는 것은 "메시지가 어떤 관을 타고 흐르는가"뿐입니다.**

### 13.1 stdio와 HTTP는 무엇이 다른가

| | stdio | Streamable HTTP |
|---|---|---|
| 서버를 누가 띄우나 | **클라이언트가 자식 프로세스로** 직접 실행 | 사람이 **미리** 띄워 둔다 |
| 준비 작업 | 없음 (명령 한 줄로 끝) | 서버를 먼저 실행해야 함 |
| 연결 수 | 1:1 (클라이언트 하나에 서버 하나) | 여러 클라이언트가 접속 가능 |
| 서버 수명 | 클라이언트가 끝나면 같이 종료 | 계속 살아 있음 |
| 통로 | 자식 프로세스의 stdin/stdout | HTTP `POST /mcp` (응답은 SSE) |
| stdout 사용 | **금지** (프로토콜 채널) | 자유 (프로토콜은 소켓으로 감) |
| 원격 접속 | 불가 (같은 머신) | 가능 |

**HTTP가 유리한 상황**은 이렇습니다.

- 데모에서 "서버가 살아 있고 클라이언트가 붙는다"는 그림을 보여주고 싶을 때
- 서버를 한 번 띄워 두고 **여러 번 실행**하며 브라우저 세션을 재사용하고 싶을 때
- 다른 언어로 만든 클라이언트, 또는 다른 머신에서 붙여 볼 때
- 서버 로그를 한 터미널에 계속 띄워 놓고 관찰하고 싶을 때

반대로 **stdio가 편한 상황**은 "그냥 한 번 돌려보고 싶을 때"입니다. 준비할 게 없으니까요.
그래서 이 저장소의 기본값은 여전히 stdio입니다.

> **SDK 버전을 바꾸지 않았습니다.** 설치된 `mcp 2.1.0` 이 이미 Streamable HTTP를 지원합니다.
> HTTP를 쓰려고 새 라이브러리를 깔거나 버전을 올릴 필요는 없었습니다.

### 13.2 서버 — `http_server.py` 읽기

파일: [`mcp_/http_server.py`](../src/toolsdemo/mcp_/http_server.py)

가장 중요한 줄은 맨 위의 import입니다.

```python
from .server import SERVER_NAME, server
```

**10장에서 만든 그 `server` 객체를 그대로 가져옵니다.** `on_list_tools` 도 `on_call_tool` 도
새로 쓰지 않습니다. 도구 구현은 말할 것도 없습니다. 이 파일이 하는 일은 그 서버를
HTTP라는 관에 꽂는 것뿐입니다.

```python
def build_app() -> Starlette:
    """registry 를 그대로 노출하는 Streamable HTTP ASGI 앱을 만든다."""
    app = server.streamable_http_app(
        streamable_http_path=settings.mcp_http_path,  # 기본 "/mcp"
        host=settings.mcp_http_host,
    )
    _attach_browser_cleanup(app)
    return app
```

`server.streamable_http_app(...)` 은 SDK가 제공하는 헬퍼로, **Starlette 웹 앱**을 돌려줍니다.
그 안에 `/mcp` 라우트 하나와 세션 관리자가 들어 있습니다. 우리가 JSON-RPC를 직접 파싱하거나
세션 ID를 관리하는 코드는 **한 줄도 없습니다.**

그다음은 평범한 웹 서버 실행입니다.

```python
def serve() -> None:
    uvicorn.run(
        build_app(),
        host=settings.mcp_http_host,
        port=settings.mcp_http_port,
        log_level=settings.log_level.lower(),
    )
```

#### 브라우저 정리를 왜 따로 감쌌나

stdio 판에서는 `serve()` 의 `finally` 에서 `close_browser()` 를 불렀습니다(10.5절).
HTTP 판에서는 그 자리가 없습니다. 서버가 uvicorn의 생명주기를 따르기 때문입니다.

```python
def _attach_browser_cleanup(app: Starlette) -> None:
    base_lifespan = app.router.lifespan_context  # SDK 가 이미 넣어 둔 lifespan

    @contextlib.asynccontextmanager
    async def lifespan(app_):
        async with base_lifespan(app_):  # 세션 매니저를 그대로 구동하고
            try:
                yield
            finally:
                await close_browser()  # 끝날 때 브라우저를 닫는다

    app.router.lifespan_context = lifespan
```

**왜 `on_shutdown` 을 쓰지 않았을까요?** SDK가 만들어 준 앱은 이미 자체 lifespan
(세션 매니저 구동)을 갖고 있고, Starlette는 lifespan이 지정되면 `on_startup`/`on_shutdown`
핸들러를 실행하지 않습니다. 그래서 **기존 lifespan을 감싸는** 방식을 썼습니다.

> 남의 코드가 만들어 준 객체에 내 정리 로직을 끼워 넣어야 할 때 자주 쓰는 패턴입니다.
> "덮어쓰기"가 아니라 "감싸기"라는 점이 중요합니다. `async with base_lifespan(app_)` 을
> 빼먹으면 세션 매니저가 시작되지 않아 서버가 응답하지 않습니다.

#### stdout 규칙은 여기서 풀린다

10.6절에서 "서버 경로에서 `print()` 금지"라고 했습니다. **HTTP에서는 해당하지 않습니다.**
프로토콜이 소켓으로 흐르므로 stdout은 그냥 로그 출력 자리입니다. 실제로 uvicorn이
`INFO: Uvicorn running on http://127.0.0.1:8931` 같은 줄을 stdout에 찍습니다.

다만 이 저장소는 도구 로그를 stdio 판과 **동일하게** `logging` 으로 남깁니다.
두 트랜스포트의 로그 모양이 같아야 비교가 쉽기 때문입니다.

> **보안 메모:** 이 서버에는 인증이 없습니다. 기본 바인딩은 루프백(`127.0.0.1`)이며
> **로컬 테스트/데모 전용**입니다. `MCP_HTTP_HOST=0.0.0.0` 으로 외부에 열지 마세요.

### 13.3 클라이언트 — 분기는 딱 한 곳

파일: [`mcp_/client_agent.py`](../src/toolsdemo/mcp_/client_agent.py)

```python
def client_target() -> StdioServerParameters | str:
    """MCP 접속 대상. 문자열이면 Streamable HTTP URL, 아니면 stdio 로 띄울 서버 파라미터."""
    if settings.mcp_transport == "http":
        return settings.mcp_http_endpoint  # "http://127.0.0.1:8931/mcp"
    return server_params()  # 기존 stdio 파라미터
```

반환 타입이 두 가지인 것이 핵심입니다. **문자열이냐 아니냐로 트랜스포트가 정해집니다.**

그리고 실제 사용처는 이렇게 한 줄 바뀌었을 뿐입니다.

```python
async def run(query: str) -> int:
    async with Client(client_target()) as client:     # 전에는 Client(server_params())
        listed = await client.list_tools()            # → POST /mcp  (tools/list)
        ...
                response = await client.call_tool(name, arguments)   # → POST /mcp  (tools/call)
```

`list_tools()` 와 `call_tool()` 을 부르는 코드는 **그대로**입니다. 11장에서 읽은 그 코드입니다.

#### SDK 안에서 무슨 일이 일어나나

`Client` 생성자가 인자 **타입만 보고** 트랜스포트를 고릅니다. SDK(`mcp/client/client.py`)의
실제 코드입니다.

```python
if isinstance(srv, Server):
    self._connect = _connect_inproc(srv)  # 테스트용 인프로세스
elif isinstance(srv, str):
    self._connect = _connect_transport(streamable_http_client(srv))  # ← HTTP
elif isinstance(srv, StdioServerParameters):
    self._connect = _connect_transport(stdio_client(srv))  # ← stdio
```

우리가 문자열을 넘기면 두 번째 가지를 탑니다. **세션 ID 관리, SSE 파싱, 재연결은 전부
SDK 몫**이고 우리 코드에는 HTTP를 다루는 부분이 없습니다.

### 13.4 설정

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `MCP_TRANSPORT` | `stdio` | `stdio` \| `http` |
| `MCP_HTTP_HOST` | `127.0.0.1` | 서버 바인딩 주소 |
| `MCP_HTTP_PORT` | `8931` | 포트 |
| `MCP_HTTP_PATH` | `/mcp` | 엔드포인트 경로 |
| `MCP_HTTP_URL` | (없음) | 접속 주소를 통째로 지정할 때만. 주면 위 세 값보다 우선 |

접속 주소는 [`config.py`](../src/toolsdemo/config.py)의 `mcp_http_endpoint` 가 조립합니다.

```python
@property
def mcp_http_endpoint(self) -> str:
    if self.mcp_http_url:
        return self.mcp_http_url
    host = self.mcp_http_host
    if host in ("0.0.0.0", "::", "[::]"):  # 바인딩 주소는 접속 주소가 아니다
        host = "127.0.0.1"
    return f"http://{host}:{self.mcp_http_port}{self.mcp_http_path}"
```

와일드카드를 루프백으로 바꾸는 부분은 16.3절의 `OLLAMA_HOST` 함정과 **똑같은 문제**를
막는 것입니다. `0.0.0.0` 은 "모든 인터페이스에서 듣겠다"는 서버 쪽 표현이지,
클라이언트가 접속할 수 있는 주소가 아닙니다.

### 13.6 브라우저는 어디에서 뜨나

12.2절의 그림에 HTTP 판을 더하면 이렇습니다.

```
[ Phase 2 · HTTP ]  프로세스 3개
┌──────────────────────────┐   HTTP     ┌──────────────────────────┐
│ client_agent.py          │  POST /mcp │ mcp_/http_server.py      │
│   OllamaAgent 루프        │◀──────────▶│   = server.py 의 핸들러   │
│   client.call_tool()     │            │   → booking.py           │
└──────────────────────────┘            │   Playwright ← 여기서 뜬다 │
        │ HTTP                          └──────────────────────────┘
        ▼                                          │
     Ollama (모델)                                  ▼
                                            mock 사이트 (별도 프로세스)
```

브라우저는 stdio 때와 마찬가지로 **서버 쪽**에서 뜹니다. 달라지는 건 그 서버가
클라이언트보다 **오래 산다**는 점입니다. 클라이언트를 두 번 실행하면 같은 서버,
같은 브라우저 세션을 이어서 쓰게 됩니다. 데모에서는 편하지만,
**앞 실행의 화면 상태가 남아 있다**는 뜻이기도 하니 헷갈리면 서버를 재시작하세요.

### 13.7 어떻게 테스트하나

#### (1) 자동 테스트 — 가장 빠르고 준비물이 없다

```powershell

pytest -q -m "not llm"               # 26 passed (stdio 포함 전체)
```

[`tests/test_mcp_http.py`](../tests/test_mcp_http.py)는 **빈 포트를 찾아 uvicorn을 백그라운드
스레드로 띄우고** URL로 접속합니다. LLM도 브라우저도 mock 사이트도 필요 없습니다.

```python
@pytest.fixture(scope="module")
def http_endpoint():
    port = _free_port()
    config = uvicorn.Config(build_app(), host="127.0.0.1", port=port, log_level="warning")
    server = uvicorn.Server(config)
    thread = threading.Thread(target=server.run, daemon=True)
    thread.start()
    ...
    yield f"http://127.0.0.1:{port}/mcp"
```

검사 항목은 12.3절의 stdio parity 테스트와 **같은 네 가지**입니다.

| 검사 | 보장하는 것 |
|---|---|
| `list_tools` vs registry | HTTP로 노출된 도구 집합·설명·스키마가 registry와 동일 |
| Ollama 스키마 비교 | 모델에게 보여주는 `tools` 배열이 Phase 1과 완전히 동일 |
| `call_tool("get_today")` | HTTP 왕복이 실제로 dict를 돌려줌 |
| 잘못된 날짜로 호출 | 실패가 프로토콜 오류가 아니라 `{"ok": false}` 페이로드로 옴 |

#### (2) 서버가 살아 있는지 — curl 한 줄

```powershell
curl.exe -s -i http://127.0.0.1:8931/mcp
```

```
HTTP/1.1 400 Bad Request
{"jsonrpc":"2.0","id":null,"error":{"code":-32600,"message":"Bad Request: Missing session ID"}}
```

**이 400이 정상입니다.** Streamable HTTP는 `initialize` 로 세션을 열지 않은 요청을 받지
않습니다. 이 JSON이 오면 서버는 살아 있는 것이고, 아무 응답도 없으면 서버가 안 뜬 것입니다.

#### (3) 프로토콜을 눈으로 보기 — curl 3단계

9.3절에서 개념으로만 본 JSON-RPC를 직접 주고받아 봅니다.

```powershell
# 1) initialize — 응답 헤더의 mcp-session-id 를 받아 둔다
curl.exe -s -D hdr.txt -X POST http://127.0.0.1:8931/mcp `
  -H "Content-Type: application/json" -H "Accept: application/json, text/event-stream" `
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'

# 2) 이후 요청에는 헤더로 세션을 붙인다
#    -H "mcp-session-id: <받은 값>"
# 3) tools/list, tools/call 호출
```

실제 응답입니다.

```
# initialize
event: message
data: {"jsonrpc":"2.0","id":1,"result":{"capabilities":{"tools":{"listChanged":false}},
       "instructions":"기차 조회부터 예약(좌석 확보)까지 …",
       "protocolVersion":"2025-06-18",
       "serverInfo":{"name":"toolsdemo-booking","title":"기차 예약 도구","version":"0.1.0"}}}

# tools/call get_today
data: {"jsonrpc":"2.0","id":3,"result":{"content":[{"text":"{\"ok\": true, \"today\": \"2026-08-29\", …}","type":"text"}],"isError":false}}
```

여기서 세 가지가 눈으로 확인됩니다.

1. 응답이 **SSE 형식**(`event: message` / `data: ...`)으로 온다
2. 10.4절에서 넣은 `instructions` 와 `serverInfo` 가 그대로 전달된다
3. 도구 결과가 **JSON 문자열이 담긴 텍스트 콘텐츠**다 — 11.4절에서 `json.loads` 로 푸는 그것

> **와이어에서는 이름이 다릅니다.** 스키마 필드가 파이썬 API에서는 `input_schema` 인데
> 실제 전송에서는 `inputSchema`(camelCase)로 나갑니다. 같은 값의 표기 차이입니다.

#### (4) 전체 에이전트 — 13.5절 그대로

stdio와 비교하려면 `$env:MCP_TRANSPORT="stdio"` 로 바꿔 같은 질의를 돌립니다.
예약번호는 mock 사이트가 매번 새로 발급하므로 달라지지만,
**도구 순서와 호출 횟수는 같아야** 합니다. 다르면 트랜스포트가 아니라 다른 데 문제가 있는 것입니다.

### 13.8 정리 — 무엇이 같고 무엇이 다른가

| | stdio | HTTP |
|---|---|---|
| 도구 구현 (`booking.py`) | 동일 | 동일 |
| MCP 핸들러 (`server.py`) | 동일 | 동일 |
| 에이전트 루프 (`ollama_client.py`) | 동일 | 동일 |
| 모델에게 보이는 `tools` 배열 | 동일 | 동일 |
| 진입점 | `mcp_/server.py` | `mcp_/http_server.py` |
| 클라이언트가 넘기는 값 | `StdioServerParameters` | URL 문자열 |
| 서버 기동 | 클라이언트가 자동 | 사람이 미리 |
| 프로세스 수 | 2 | 3 (mock 사이트 제외) |

**우리가 새로 쓴 코드는 `http_server.py` 한 파일과 `client_target()` 한 함수뿐**입니다.
도구를 추가해도 이 파일들은 손댈 일이 없습니다 — 10.7절과 같은 이유입니다.

#### 자주 막히는 곳

### 14.1 각 줄이 어디서 나왔나

| 로그 | 코드 위치 | 그때 무슨 일이 |
|---|---|---|
| `[Phase 1 · native tools] …` | `agent_tools.py` 의 `print(...)` | 시작 배너 |
| `모델=qwen3.6:27b 도구=7개` | `ollama_client.py` 의 `logger.info` | 루프 진입, 도구 7개 전달 |
| `[tool] → get_today({})` | `registry.call_tool` 의 호출 로그 | 모델이 `get_today` 를 부르기로 결정 |
| `[tool] ← get_today: {...}` | 같은 함수의 응답 로그 | 우리 코드가 실행해 결과를 얻음 |
| `브라우저 시작 (headless=False…)` | `browser.py` 의 `_start()` | `search_trains` 가 처음 페이지를 요구한 순간 |
| `도구 호출 없음 → 종료 (step 6)` | 루프의 종료 분기 | 모델이 더는 도구를 안 부름 |

### 14.2 "도구 호출 5회 / 반복 6회"의 의미

반복이 호출보다 하나 많습니다. 왜일까요?

```
반복 1: 모델 → get_today 호출          (도구 1회)
반복 2: 모델 → search_trains 호출      (도구 2회)
반복 3: 모델 → select_train 호출       (도구 3회)
반복 4: 모델 → fill_passenger 호출     (도구 4회)
반복 5: 모델 → confirm_booking 호출    (도구 5회)
반복 6: 모델 → 도구 없음, 최종 답변      ← 여기서 종료
```

**마지막 한 바퀴는 도구를 부르지 않고 사람에게 답하기 위한 것**입니다.
6.1절의 종료 조건이 그대로 보입니다.

### 14.3 모델이 스스로 판단한 것들

이 로그에서 눈여겨볼 대목은 **우리가 시키지 않은 판단**입니다.

- 사용자는 "내일"이라고만 했는데 모델이 **먼저 `get_today` 를 불렀습니다.**
  → `get_today` docstring의 "'내일' 같은 표현을 날짜로 바꿀 때 먼저 호출한다" 때문입니다.
- "오전 9시"를 `depart_after: '09:00'` 으로 바꿨습니다.
  → 시스템 프롬프트 4번 규칙 + 인자 설명의 "HH:MM 형식" 때문입니다.
- 22편 중 `3105` 를 골랐습니다.
  → 시스템 프롬프트 5번 "잔여석이 있는 가장 이른 열차" 때문입니다.
- 이름을 안 줬는데 `홍길동` 을 썼습니다.
  → 시스템 프롬프트 6번의 기본 승객 이름 때문입니다.
- **결제를 시도하지 않았습니다.**
  → 부를 도구가 없기 때문입니다(8.6절).

즉 에이전트의 행동은 **코드가 아니라 도구 설명과 프롬프트가 만든 결과**입니다.
행동을 바꾸고 싶으면 그 둘을 고치세요.

### 14.4 Phase 2 로그와의 차이

```
[Phase 2 · MCP]  model=qwen3.6:27b  target=mock  mcp_tools=7
```

예를 들어 "현재 선택된 열차 정보를 알려주는 도구"를 추가한다고 합시다.

### 1단계 — 함수를 쓴다

[`tools/booking.py`](../src/toolsdemo/tools/booking.py) 맨 아래에 추가합니다.

```python
@tool
async def get_selection() -> dict[str, Any]:
    """지금까지 선택한 열차와 조회 조건을 알려준다. 흐름이 꼬였을 때 현재 상태 확인용.

        selected: 선택된 열차번호 (없으면 null), last_query: 마지막 조회 조건
    """
    return {
        "ok": True,
        "selected": _state["selected"],
        "last_query": _state["last_query"],
        "option_count": len(_state["options"]),
    }
```

- [ ] `@tool` 을 붙였는가

- [ ] 인자가 있다면 `Args:` 에 **형식과 예시**를 썼는가
- [ ] `dict` 를 반환하는가 (예외를 던지지 않는가)
- [ ] 반환값이 전부 JSON으로 바꿀 수 있는 값인가

### 16.1 `ERR_CONNECTION_REFUSED at http://127.0.0.1:8765/`

```
playwright._impl._errors.Error: Page.goto: net::ERR_CONNECTION_REFUSED at http://127.0.0.1:8765/
[tool] ← search_trains: {'ok': False, 'error': 'Error: Page.goto: net::ERR_CONNECTION_REFUSED ...'}
```


이때 브라우저 창이 잠깐 떴다가 닫히는 것도 **정상 동작**입니다. 접속에 실패해 루프가

### 16.2 모델이 도구를 안 부르고 말로만 답한다

가장 흔한 증상입니다. 순서대로 의심하세요.

1. **도구 docstring** — 언제 쓰는 도구인지 한 줄 요약에 드러나 있습니까?
   인자 형식이 적혀 있습니까? (3장의 약속 3)
2. **모델이 tools를 지원하는가** — `ollama show <모델명>` 의 `Capabilities` 목록에
   `tools` 가 있어야 합니다. 없는 모델은 `tools` 를 줘도 무시합니다.

   ```powershell
   ollama show qwen3.6:27b     # Capabilities: completion / vision / tools / thinking
   ```
3. **시스템 프롬프트** — "반드시 도구를 호출하세요. 말로만 설명하지 마세요" 같은 지시가
   있습니까? 이 저장소 프롬프트 1번 규칙이 그것입니다.

순서가 중요합니다. **프롬프트보다 docstring을 먼저 고치세요.**

### 16.3 `ConnectionError` — Ollama에 접속이 안 된다

이 PC의 시스템 환경변수는 `OLLAMA_HOST=0.0.0.0:11434` 입니다.
이건 서버가 **어디에 귀를 열지**(바인딩) 정하는 값인데, 클라이언트가 이걸 그대로
**접속 주소**로 쓰면 실패합니다. `0.0.0.0` 은 "모든 인터페이스"라는 뜻이지 접속할 수 있는
주소가 아니기 때문입니다.

[`config.py`](../src/toolsdemo/config.py)의 `_normalize_ollama_host()` 가 이걸 처리합니다.

```python
for wildcard in ("0.0.0.0", "[::]", "::"):
    if hostport == wildcard or hostport.startswith(wildcard + ":"):
        hostport = "127.0.0.1" + hostport[len(wildcard) :]
        break
```

와일드카드를 루프백(`127.0.0.1`)으로 바꾸고, 스킴(`http://`)이 없으면 붙여 줍니다.
**이 정규화를 지우지 마세요.** 지우면 이 PC에서 바로 `ConnectionError` 가 납니다.

### 16.5 MCP 통신이 이유 없이 실패한다

**서버 코드 경로에서 `print()` 를 썼는지 확인하세요.** stdout은 JSON-RPC 전용입니다(9.3절).
단, 이 제약은 **stdio 에서만** 해당합니다. HTTP 트랜스포트에서는 프로토콜이 소켓으로
흐르므로 stdout 이 자유롭습니다(13.2절).
디버깅용 출력은 반드시 `logging`(stderr)으로 바꾸세요.

```python
print("여기까지 옴")  # ❌ 프로토콜이 깨진다
logger.info("여기까지 옴")  # ✅ stderr로 나간다
```

한글이 깨지면서 실패한다면 `PYTHONIOENCODING=utf-8` 을 확인하세요(11.1절).

### 16.6 인터넷의 MCP 예제가 안 돌아간다

거의 대부분 **SDK 1.x 예제**입니다. 이 저장소는 2.x입니다(10.8절 대조표).
`@server.list_tools()` 나 `inputSchema=` 가 보이면 1.x 예제입니다.

### 16.7 모델이 스키마에 없는 인자를 보낸다

정상입니다. `call_tool` 이 걸러내고 경고만 남깁니다(7장).

```
[tool] search_trains: 미정의 인자 무시 ['train_type']
```

**같은 경고가 반복된다면** 모델이 그 인자를 필요로 한다는 신호입니다.
docstring을 손보거나, 정말 필요하면 인자로 추가하세요.

### 16.8 도구 순서를 어긴다

```
[tool] ← select_train: {'ok': False, 'error': '조회 결과가 없습니다. search_trains 를 먼저 호출하세요.'}
```

이것도 설계된 동작입니다(8.1절). 모델이 이 메시지를 읽고 스스로 복구합니다.
매번 반복된다면 시스템 프롬프트의 순서 규칙과 docstring을 함께 점검하세요.

## 17장. 용어집

| 용어 | 뜻 |
|---|---|
| **LLM** | 대규모 언어 모델. 텍스트를 생성하는 것이 유일한 능력입니다. |
| **Ollama** | 로컬 PC에서 LLM을 돌려주는 프로그램. `http://127.0.0.1:11434` 로 API를 제공합니다. |
| **tool calling / function calling** | 모델에게 함수 목록을 주고, 모델이 "이걸 이 인자로 부르고 싶다"는 JSON을 내게 하는 기능. **실행은 우리 코드가 합니다.** |
| **tools 배열** | 매 요청에 함께 보내는 도구 명세 목록. 이름·설명·JSON Schema로 구성됩니다. |
| **JSON Schema** | "이 데이터는 이런 모양이어야 한다"를 JSON으로 적은 명세. 인자 타입·필수 여부·설명을 담습니다. |
| **에이전트 루프** | 모델에게 묻고 → 도구를 실행하고 → 결과를 다시 넣는 반복문. 모델이 도구를 안 부를 때 끝납니다. |
| **messages** | 대화 전체를 담은 리스트. `system`/`user`/`assistant`/`tool` 역할이 있습니다. |
| **MCP** | Model Context Protocol. LLM 앱이 외부 도구·데이터에 연결하는 방식을 표준화한 프로토콜. |
| **호스트 / 클라이언트 / 서버** | 각각 LLM을 굴리는 앱 / 프로토콜로 대화하는 부분 / 도구를 제공하는 프로세스. |
| **stdio 트랜스포트** | 서버를 자식 프로세스로 띄우고 표준 입출력으로 통신하는 방식. 이 저장소가 쓰는 방식입니다. |
| **JSON-RPC 2.0** | `{"method": ..., "params": ..., "id": ...}` 형태로 원격 호출을 주고받는 규약. |
| **직렬화 / 역직렬화** | 파이썬 값 → JSON 문자열 / JSON 문자열 → 파이썬 값. `json.dumps` / `json.loads`. |
| **Playwright** | 브라우저를 코드로 조작하는 라이브러리. 이 저장소는 async + Chromium을 씁니다. |
| **headless** | 브라우저 창을 화면에 띄우지 않고 도는 모드. 데모 녹화 때는 `HEADLESS=false` 로 끕니다. |
| **어댑터(Adapter)** | 사이트마다 다른 부분(CSS 셀렉터, 조작 순서)을 흡수하는 계층. `tools/sites/` 에 있습니다. |
| **싱글턴(Singleton)** | 프로세스 전체에서 인스턴스를 하나만 두는 방식. 여기서는 브라우저 세션. |
| **데코레이터** | 함수를 감싸 기능을 더하는 문법. `@tool` 이 그것입니다. |
| **코루틴** | `async def` 로 만든 함수. `await` 로 실행합니다. |
| **registry(레지스트리)** | 도구 명세를 모아 둔 목록. 이 저장소의 단일 진실 원천입니다. |
| **parity 테스트** | 두 경로가 동일함을 기계적으로 검증하는 테스트. `tests/test_parity.py`. |
